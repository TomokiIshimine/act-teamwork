# setup-fields — 初期設定で決める項目の説明

## 読み手と使い方

setup のメインと help が読む。どの節をいつ、どう使うかは読む側が決める。

各節に書かれていること:

- 項目の一覧: 項目ごとの用途（使う人向けの説明）、書かれる場所、後から変えられるか。
- 質問に添える説明: 項目を尋ねるときに添える 1〜2 文。
- 役割の値: 役割の値ごとの説明と、保存先の作成・取り込み・更新ができるか。
- スキーマ版と保存先の更新: スキーマ版の意味と記録の場所、保存先の更新で起きることと、更新できる役割。
- 自分で入力するときの条件と例: 候補から選ばずに入力するときに満たす条件と例。

扱わないもの:

- 尋ねる順序、経路ごとに尋ねる項目、確認の取り方（保存先更新の経路での役割ごとの選択肢を含む）。setup が決める。
- 推奨値・候補の作り方（プロジェクトキーを名前から略す手順、候補の件数、確信度など）。setup 側が持つ。
- 版ごとの具体的な移行内容、版の番号、DB やプロパティの名前。アダプタのスキーマ定義が正で、setup の変更計画フォームで示す。

## 項目の一覧

「何に使われるか」には使う人向けの説明だけを書き、ファイルのパスやキー名は「どこに書かれるか」にだけ置く。

| 項目 | `02_inputs.yaml` のキー | 何に使われるか | どこに書かれるか | 後から変えられるか |
| --- | --- | --- | --- | --- |
| 共有フォルダのパス | `root` | プロジェクトの共有フォルダ（Google ドライブの同期先など）の、この PC 上の場所。メンバー共通のプロジェクト設定をここに置き、ここで探す。あるかどうかで、新しいプロジェクトの作成か参加かが決まる。資料・成果物の置き場所にもなる。 | 個人設定 `projects.<キー>.root`（PC ごとに違う） | 変えられる。PC や同期先を替えたら、新しい場所を指定して setup を再実行すると更新される。 |
| プロジェクト名 | `project_name` | プロジェクトを人が見分けるための名前。プロジェクトの一覧やトップページに表示され、ナレッジに付けるプロジェクトのタグにもなる。確認フォームで「どのプロジェクトに書くか」を示すときにも出る。 | 個人設定 `projects.<キー>.name`、`project.yaml` の `project.name`、共通のプロジェクト一覧、トップページ、タグ `プロジェクト:<名前>` | 新しいプロジェクトの作成のときに決める。参加・保存先更新ではメンバー共通の設定の値を使い、setup では変えられない（変えたいときはマネージャーに確認する）。 |
| プロジェクトキー | `project_key` | 決定事項・タスクなどの ID の頭に付く短い記号（例: `FAQ-DEC-0012` の `FAQ`）。参加しているプロジェクトを見分ける記号にもなる。 | 個人設定 `projects` のキー、`project.yaml` の `project.key` | 事実上変えられない。ID に含まれるため、作ったあとに変えると既存の ID と合わなくなる。setup には作成後にキーを変える手段が無い。 |
| 役割 | `roles` | このプロジェクトでの自分の役割（兼任できる）。ワークフローが、確定として書くか、提案として書くか、判断依頼にするかを決める手がかりになる。保存先の作成・取り込み・更新ができるかもこれで決まる。 | 個人設定 `projects.<キー>.roles`。保存先のメンバー一覧にも登録される（「役割の値」） | 新しいプロジェクトの作成か参加のときに決める。参加済みのプロジェクトで setup を再実行しても変わらない（個人設定の値を使う）。メンバー一覧の役割はマネージャーが設定する。 |
| クライアント | `client` | このプロジェクトの顧客。トップページの概要に書かれ、ナレッジに付けるクライアントのタグになる。このタグが付いたナレッジは、プロジェクトの外からでもクライアント名で引ける。 | `project.yaml` の `project.client`、共通のクライアント一覧、トップページの概要、タグ `クライアント:<名前>` | 新しいプロジェクトの作成のときに決める。参加・保存先更新では setup では変えられない（変えたいときはマネージャーに確認する）。 |
| 保存先の場所 | `store_location` | 決定事項・タスク・議事録などを置く場所。Notion では、渡したページの下に ACT の DB 一式とトップページを作るか、そのページにある既存の DB を取り込む。 | 作られた DB の場所が `project.yaml` の `stores` に記録される | 新しいプロジェクトの作成のときに決める。参加・保存先更新ではメンバー共通の設定の値を使い、setup では変えられない（変えたいときはマネージャーに確認する）。 |
| 保存先の種類 | `store_type` | 保存先をどのサービス（Notion など）で読み書きするかを決める。保存先の URL から決まる（Notion の URL なら Notion）。 | `project.yaml` の `stores` の各 `adapter`、個人設定 `projects.<キー>.accounts` のキー | 保存先の場所から決まり、これだけを変えることはできない。 |
| 経路 | `route` | setup が何をするかを決める。新規プロジェクト作成／既存プロジェクトへの参加／参加済みプロジェクトの保存先更新のどれか。共有フォルダにメンバー共通のプロジェクト設定があるかと、自分の個人設定から決まる。 | 設定ファイルには書かない（setup の実行中だけ使う） | 設定には残らない。setup を実行するたびに、そのときの設定から決まる。 |
| スキーマ版 | （なし） | 保存先の DB の形（プロパティの構成や本文の見出し）の版。プラグインの更新とともに新しい版が出る。 | `project.yaml` の `schema_version`（保存先の種類ごと）、保存先側の記録（Notion ならトップページの子ページ「🔧 ACT 設定」） | `manager` か `business_owner` が setup を再実行して保存先を更新したときに上がる。 |

保存先の種類・経路・スキーマ版は、ほかの値や設定から決まるので、自分では入力しない。

## 質問に添える説明

項目を尋ねるときに添える 1〜2 文。

- 共有フォルダのパス: 「プロジェクトの共有フォルダ（Google ドライブの同期先など）の、この PC 上の場所です。メンバー共通のプロジェクト設定をここで探し、あれば参加、無ければ新しいプロジェクトの作成になります。」
- プロジェクト名: 「プロジェクトを見分けるための名前です。プロジェクトの一覧やトップページに表示され、ナレッジに付けるプロジェクトのタグにもなります。」
- プロジェクトキー: 「決定事項やタスクの ID の頭に付く短い記号です（例: FAQ-DEC-0012 の FAQ）。作ったあとは変えられないので、慎重に選んでください。」
- 役割: 「このプロジェクトでのあなたの役割です（兼任できます）。ワークフローが、確定として書くか、提案や判断依頼にするかを決めるのに使います。保存先の作成・更新ができるのはマネージャーとビジネスオーナーです。」
- クライアント: 「このプロジェクトの顧客です。ナレッジにクライアントのタグが付き、プロジェクトの外からでもクライアント名で引けるようになります。」
- 保存先の場所: 「決定事項・タスク・議事録などを置く Notion のページの URL です。そのページの下に ACT の DB 一式とトップページを作るか、そのページにある既存の DB を取り込みます。どちらになるかはページの中身から判定し、変更計画で示します。」

## 役割の値

ここは使う人への説明で、中止や登録の判定は setup が変更計画を作るときに行う（判定の正はそちら）。

| 値 | 説明 | 保存先の作成・取り込み・更新 |
| --- | --- | --- |
| `business_owner` | ビジネスオーナー。プロジェクトの目的・制約を決め、判断依頼に答える。 | できる |
| `manager` | マネージャー。議事録・資料から決定事項とタスクを確定し、進捗を評価して報告する。保存先の作成・更新も行う。 | できる |
| `worker` | ワーカー。タスクを担い、進捗・成果物・知見・変更の要求を返す。 | できない |

- 役割は兼任できる（例: `manager` と `worker`）。プロジェクトごとに違ってよい。
- 新しいプロジェクトの作成で、役割に `manager` も `business_owner` も含まれないときは、保存先を作れないため setup は中止になる（マネージャーに作成を頼むか、役割を見直す）。
- 保存先のメンバー一覧への登録: 新しいプロジェクトの作成では、答えた役割で登録される。参加・保存先更新では（まだ登録されていなければ）`worker` で登録され、役割はマネージャーが設定する。個人設定の役割とメンバー一覧の役割が食い違うと、警告が出る。
- 個人設定の役割は自己申告で、本当にできるかどうかは保存先側の権限で決まる。

## スキーマ版と保存先の更新

### スキーマ版

- 保存先の DB の形（プロパティの構成や本文の見出し）の版。プラグインの更新とともに新しい版が出る。
- 保存先の種類ごとに `project.yaml` の `schema_version` に記録され、setup が保存先を作成・更新したときに書き換わる。保存先側（Notion ならトップページの子ページ「🔧 ACT 設定」）にも記録があり、食い違えば保存先側が正。
- `project.yaml` の記録は目安で、実際の版は保存先を点検して分かる。実際の版と、上げるときの移行内容は setup の変更計画フォームで示される。
- 版が古いままでも、旧版で安全に書ける項目は書き続けられる。古ければ警告が出る。
- 版を上げるのは、`manager` か `business_owner` が setup を再実行したとき。

### 保存先の更新

参加済みのプロジェクトで setup を再実行したとき（プラグインの更新後など）に行えること。

起きること:

- 足りない DB・プロパティを足す。
- 不要になったものは削除せず、名前に `旧_` を付けて残す。
- 入っている値は消さず、書き換えない。値を別のプロパティや本文へ移す変更があるときは、変更計画フォームで見本を示し、承認を取ってから移す。
- 何も、変更計画フォームで承認されるまで書かない。

更新できる役割:

- スキーマの更新ができるのは `manager` と `business_owner` だけ。
- 役割が `worker` だけのときはスキーマを更新できず、個人設定に関わる変更（共有フォルダのパスの更新など）だけが対象になる。版が古ければ警告が出るので、マネージャーに更新を頼む。

## 自分で入力するときの条件と例

- 共有フォルダのパス: この PC 上の絶対パス。例 `/Users/me/Google Drive/共有ドライブ/faq-poc`。
- プロジェクト名: 自由な名前。例「社内FAQ AI検証」。
- プロジェクトキー: 英大文字 2〜6 文字で、参加しているすべてのプロジェクトのキーと重ならないこと。例 `FAQ`、`SALES`。保存先で既に使われている ID の頭と重なるときは、変更計画で別の候補が示される。
- クライアント: 会社（法人）単位の名前にし、部署名は入れない。例「みなと商事」。共通のクライアント一覧に同じ名前があればそれを使い、無ければ新しく作る（変更計画で示す）。社内のプロジェクトでクライアントを付けるときは自社名にする。付けないときは「クライアントなし」を選ぶと空になる。
- 保存先の URL: Notion のページの URL（`notion.so` か `notion.site`）。例 `https://www.notion.so/xxxx`。Notion 以外の URL には対応していない。
