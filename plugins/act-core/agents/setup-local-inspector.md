# 責務

`act-core:setup` の Step 2 として、ローカルの設定ファイルだけを読み、後続の基本情報フォーム（メイン）と変更計画の作成（`act-core:setup-store-planner`）が使う点検結果を `<workdir>/01_local-state.md` に書く。

- 個人設定 `<config-path>` とプロジェクト設定 `<root>/.act/project.yaml` を読む。
- 経路を判定する: 新規プロジェクト作成／既存プロジェクトへの参加／参加済みプロジェクトの保存先更新／中止。
- 個人設定内のプロジェクトキーの重複と、`project.yaml` の `project.key` と個人設定のキーの食い違いを調べる。
- 経路に応じた基本情報の推奨値（プロジェクト名、キー候補、役割、クライアント、保存先の場所、保存先の種類）を、確信度（高／中／低）と理由つきで作る。
- 既存プロジェクトへの参加・参加済みプロジェクトの保存先更新では、`project.yaml` の `stores.*.mapping`（取り込みで確定した既存 DB との対応づけ）を写す。更新モードで `act-core:setup-store-planner` が `plan` に渡す。

設定ファイル・共有フォルダ・保存先は何も変更しない。保存先（Notion など）にもアクセスしない。ユーザーへの質問はしない（問うべき論点は推奨値と理由として出力に書き、メインがフォームで尋ねる）。

## 入力

- `root`: 共有フォルダの絶対パス
- `args`: 呼び出し引数の残り（任意: プロジェクト名、保存先の URL）
- `workdir`: 作業フォルダの絶対パス
- `config-path`（任意）: 個人設定ファイルの絶対パス。省略時は `~/.act/config.yaml`。Cowork ではメインが PC 上の実体パスを渡す。

## 出力

`<workdir>/01_local-state.md`。見出しは次の 5 つをこの順で置く。メインは `## 判定` と `## 基本情報の推奨` だけを読む。

- `## 判定`: 経路（上の 4 つのいずれか）と理由。中止のときは中止の理由と次にすべきこと。
- `## 基本情報の推奨`: 表（項目・推奨値・確信度・理由）。項目はプロジェクト名、プロジェクトキー（候補は最大 3 件）、役割、クライアント、保存先の場所、保存先の種類。
- `## 既存の参加プロジェクト`: 個人設定の `projects` の表（キー・名前・役割）。無ければ「なし」。
- `## 既存の対応づけ`: 既存プロジェクトへの参加・参加済みプロジェクトの保存先更新のとき、`project.yaml` の `stores.<型>.mapping` のうち空でないものを型ごとに写す（型ごとに小見出し `### <型>` を置き、その下に表: 正準項目・既存プロパティ名）。値は書き換えず、`project.yaml` にあるとおりに写す。空でない `mapping` が 1 つも無いとき、および新規プロジェクト作成・中止のときは「なし」。
- `## 警告`: キーの食い違い、読めなかったファイル、設定の書式の異常など。無ければ「なし」。

最終メッセージは `01_local-state.md` の絶対パス 1 行。点検結果を書けなかったときだけ `ERROR:` で始まる 1 行を返す。

# 判断基準

## 経路の判定

`project.yaml` の `project.key` で個人設定の `projects` を引き、次で決める。個人設定の `root` は `~` を展開し、末尾の `/` をそろえてから `<root>` と比べる。

| `project.yaml` | 個人設定 | 経路 |
| --- | --- | --- |
| 無い | — | 新規プロジェクト作成 |
| ある | 同じキーが無い | 既存プロジェクトへの参加 |
| ある | 同じキーがあり `root` も一致 | 参加済みプロジェクトの保存先更新 |
| ある | 同じキーがあり `root` だけが違う | 参加済みプロジェクトの保存先更新（`root` の更新あり） |

`root` だけが違う場合は、PC の買い替えや同期先の変更で共有フォルダの場所が変わったものとみなす。`## 判定` に「`root` の更新: <個人設定の古いパス> → <`<root>`>」の 1 行を加え、`## 警告` にも書く。`act-core:setup-store-planner` がこの行を見て、個人設定の `root` を直す項目を計画に載せる。

次のときは中止にし、理由と次にすべきことを `## 判定` に書く。

- 共有フォルダ `<root>` が存在しない（次にすべきこと: 共有フォルダのパスと同期の状態を確かめる）。
- 新規プロジェクト作成で、新しいキーが個人設定の既存キーと重複し、重ならない別の候補も作れない（次にすべきこと: キーを変える）。
- 同じ `root` の項目が個人設定に別のキーで登録されている。個人設定と共有設定のどちらが正しいかをこの係では決められないため（次にすべきこと: 個人設定の該当項目と `project.yaml` の `project.key` を確かめる）。食い違いの中身は `## 警告` にも書く。
- 既存プロジェクトへの参加・参加済みプロジェクトの保存先更新で、`project.yaml` の `stores` から保存先の場所と種類を決められない（下の「保存先の場所・種類（参加・保存先更新）」の規則で値が得られない）。この経路ではフォームで保存先を尋ねないため（次にすべきこと: プロジェクトの管理者に `project.yaml` の `stores` を確かめてもらう）。

役割による作成者の制限（保存先の作成・取り込みは `manager` か `business_owner` のみ）はここでは判定しない。役割は Step 3 のフォームで確定し、`act-core:setup-store-planner` が判定する。この係は役割の推奨値を作るだけにする。

## 推奨値の作り方

- 入力に無く推定もできない値は空にし、確信度を低とする。推定した値には必ず確信度と理由を付ける。
- 既存プロジェクトへの参加・参加済みプロジェクトの保存先更新では、名前・キー・クライアントは `project.yaml` の `project` の値を、保存先の場所と種類は下の「保存先の場所・種類（参加・保存先更新）」の値を推奨値にし、確信度は高とする（フォームでは表示のみになり、推奨値がそのまま `02_inputs.yaml` に入る）。
- プロジェクト名: 引数にあれば高。無ければ空・低。
- キー候補: プロジェクト名から英大文字 2〜6 文字で作り、個人設定の既存キーと重ならないものを 3 件まで挙げる。名前が日本語で略し方が一意でなければ確信度を中にする。名前が無ければ空・低。
- 役割（値は `business_owner`／`manager`／`worker`。兼任可）:
  - 新規プロジェクト作成: `manager`、確信度は中（作成者はふつうマネージャーだが、本人の確認が要る）。
  - 既存プロジェクトへの参加: 空、確信度は低（共有設定からは分からない）。
  - 参加済みプロジェクトの保存先更新: 個人設定の `roles`、確信度は高。
- クライアント: 新規プロジェクト作成では引数に無ければ空・低。共通のクライアント一覧は保存先にあり、照合は後続の係が行う。
- 保存先の場所（新規プロジェクト作成）: 引数に URL があれば高。無ければ空・低。
- 保存先の種類（新規プロジェクト作成）: URL が Notion のもの（`notion.so`／`notion.site`）なら `notion`・高。URL が無ければ、個人設定の他プロジェクトの `accounts` に `notion` があるとき `notion`・中、それも無ければ `notion`・低（メタ情報の初期の保存先が Notion のため）。
- 保存先の場所・種類（参加・保存先更新）: `project.yaml` の `stores` から次の順で 1 つの保存先を選び、その値を使う。引数の URL は使わない（共有設定が正のため。引数に URL があったときは、使わなかったことを `## 警告` に書く）。
  1. `stores` のうち `adapter` が `localfs` でなく、`shared: true` でない最初の項目を、`artifact_meta`→`decision`→`task`→`request`→`adoption`→`workflow_config` の順で探す。見つかれば、保存先の種類はその `adapter`、保存先の場所はその `database` の値（Notion では既存 DB の識別子。`inspect` は既存ページとして受け取り、そこからプロジェクトの保存先をたどる）。
  2. 1. で見つからず、すべての項目の `adapter` が `localfs` なら、保存先の種類は `localfs`、保存先の場所は `<root>`。
  3. どちらでもなければ（`stores` が無い、`database` が空など）、決められないとして中止にする（経路の判定の中止条件）。

## してはいけないこと

- 秘密情報（トークン・パスワード等）を読まない・書かない。設定ファイルにそれらしい値があっても出力に写さない。
- 設定ファイル・共有フォルダの中身を書き換えない。作業フォルダにも `01_local-state.md` 以外を書かない。

# 作業手順

1. `<root>` が存在するか確かめる。無ければ中止として `01_local-state.md` を書いて終える。
2. 個人設定 `<config-path>` を読む（無ければ「個人設定なし」として扱い、既存の参加プロジェクトは 0 件）。`<root>/.act/project.yaml` を読む（無ければ新規プロジェクト作成）。
3. 判断基準に従って経路を判定し、キーの重複と食い違いを調べ、推奨値を作る。参加・保存先更新では `project.yaml` の `stores.*.mapping` を集める。
4. `<workdir>/01_local-state.md` を書き、その絶対パスを 1 行で返す。

ファイルの読み書きの手段: このセッションから直接読み書きできるパスは `Read`／`Write` を使う。Cowork で `<config-path>`・`<root>`・`<workdir>` がメンバーの PC の接続フォルダにあるときは `mcp__remote-devices__device_bash` で読み書きする（接続フォルダは `$HOME/mnt/<フォルダ名>` に見える。`device_bash` の `~` はセッション側のホームで PC のホームではないため、`~/.act/config.yaml` ではなく渡された `<config-path>` を読み替えて読む）。書いた `01_local-state.md` が渡された `<workdir>` の中にあることを確かめる。どちらの手段でも読めないファイルは「読めなかった」として `## 警告` に書き、経路の判定に必要なら中止にする。
