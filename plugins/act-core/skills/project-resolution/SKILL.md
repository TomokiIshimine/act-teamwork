# project-resolution — 対象プロジェクトの解決

一人が複数のプロジェクトに参加する前提で、ワークフローは書く前に対象プロジェクトを 1 つ決める。本スキルは決め方の規則だけを定める。どの入力を集めるか、決めた結果をどう確認するか、決められないときに誰が尋ねるかは呼び出し元のワークフローが決める。

本スキルは何も書き換えない。設定ファイルは `act-core:local-files`、保存先は `act-core:store-protocol` に従って読む。

## 入力

呼び出し元が集めて渡す。無いものは省略してよい。

| 入力 | 中身 |
| --- | --- |
| 明示の指定 | 利用者が引数やチャットで示したプロジェクトの名前かキー |
| 入力ファイルのパス | 入力ファイルの絶対パスの一覧（Cowork ではメンバーの PC 上の絶対パス） |
| 選択中のプロジェクト | セッションで選択中のプロジェクトのキー |
| 入力内容の抜粋 | 入力の内容のうち照合に使う部分（ファイルなら先頭部分、テキストなら全文か要所） |
| 個人設定 | `~/.act/config.yaml` の `projects`（キー・`name`・`roles`・`root`・`status`）と `default_project` |
| プロジェクトの概要 | 各候補の `<root>/.act/project.yaml` の `project.name`・`project.client`。保存先のトップページの概要（読めるときだけ） |

### 候補にするプロジェクト

- 個人設定の `projects` にあるプロジェクトだけを候補にする。`status: archived` のものは外す。
- 明示の指定が `archived` のプロジェクトだけに一致したときは、そのプロジェクトで決めず、「アーカイブ済み」を根拠に添えて決められない扱い（下記）にする。

## 規則の順

上から順に当てはめ、決まったところで止める。

| 規則 | 決め方 | 確信度 |
| --- | --- | --- |
| ① 明示 | 指定がキー、または名前（個人設定の `name`、`project.yaml` の `project.name`）に完全一致したら、そのプロジェクト | 高 |
| ② 共有フォルダの配下 | 入力ファイルのパスが、どのプロジェクトの `root` の配下にあるか | 高 |
| ③ 選択中 | セッションで選択中のプロジェクト | 高 |
| ④ 内容の照合 | 入力内容の抜粋と各プロジェクトの概要を照らし合わせる | 中 |
| ⑤ 既定 | 個人設定の `default_project` | 低 |

### ① 明示

- 完全一致が無く、名前・別名（プロジェクト・クライアントの一覧に登録された別名など、読める範囲）に部分一致したものは候補にする。
  - 候補が 1 件: そのプロジェクトにし、確信度は 中、確認を求める。
  - 候補が 2 件以上: 決められない扱いにする。
- 指定があるのにどれにも一致しなければ、②以降に進まず決められない扱いにする（候補は参加中の全プロジェクト）。利用者が示した指定を、別の規則で黙って置き換えない。

### ② 共有フォルダの配下

- PC 上の絶対パスどうしで比べる。接続フォルダの読み替え後の形（`$HOME/mnt/...`）では比べない。
- 個人設定の `root` が `~` で始まるときは、PC のホームで展開してから比べる。ホームが分からなければ②を使わずに③へ進む。
- 末尾の `/` をそろえ、パスの区切りの単位で配下かを判定する（`/a/proj` は `/a/project/x` の親ではない）。
- 1 つのファイルが複数の `root` の配下にあるときは、最も深い `root` を採る。
- 全ファイルが同じプロジェクトの配下なら、そのプロジェクトに決める。どの `root` の配下にも無いファイルは判定に使わない（配下にあるファイルだけで決める）。
- ファイルが別々のプロジェクトの配下にあるときは、1 つに決めない。決められない扱いにし、ファイルごとの割り当てを `per_item` に返す（呼び出し元が、プロジェクトごとに分けて実行するか利用者に選ばせる）。

### ③ 選択中

- 選択中のプロジェクトが候補にあれば、そのプロジェクトに決める。`archived` か個人設定に無ければ使わずに④へ進む。

### ④ 内容の照合

- 照合の材料: プロジェクトの名前・キー・クライアント名、保存先のトップページの概要。入力内容にそれらの語や、その案件に固有の話題が出てくるかを見る。
- 1 件だけがはっきり合えば、そのプロジェクトに決める。根拠（どの語・どの記述が合ったか）を添える。
- 2 件以上が同じ程度に合うときは、⑤に進まず決められない扱いにする。
- どれも合わなければ⑤へ進む。

### ⑤ 既定

- `default_project` が候補にあれば、そのプロジェクトに決める。
- 無いとき（未設定、`archived`、個人設定に無い）は、決められない扱いにする（候補は参加中の全プロジェクト）。

## 確認を求める条件

次のどれかに当たれば `requires_confirmation: true` を返す。呼び出し元は書き込み計画で対象プロジェクトを明示し、確認を取る（確信度ごとの扱いは `act-core:write-plan` に従う）。

- ④または⑤で決めた。
- ①の部分一致で決めた。
- `per_item` に確信度 中・低の割り当てがある。

## 決められないとき

- 推測で 1 つに決めない。`project_key` と `rule` を `null` にし、`candidates` に候補と根拠を並べて返す。
- 呼び出し元が候補を選択肢にして利用者に選ばせる。選ばれたプロジェクトは①の明示として扱ってよい。
- 人に確認できない実行（定期実行など）では、書かずに止める。

## 複数プロジェクトの内容を含む入力

1 つの入力（複数案件にまたがる会議の議事録など）に、別のプロジェクトの内容が含まれることがある。

- 入力全体のプロジェクト（主となるプロジェクト）を上の規則で決めたうえで、抽出した項目ごとにプロジェクトを割り当て、`per_item` に返す。
- 項目ごとの割り当ては④と同じ照合で行う。はっきり合えば 中、迷えば 低 とし、迷う項目は主となるプロジェクトを推奨値にする。
- 置き場所の目安: 入力の本体（ファイルそのもの）は主となるプロジェクトに置き、他のプロジェクトにはその項目（メタ情報・抽出した候補）だけを書く。本体を複数のプロジェクトに重ねて置かない。
- 書き込み計画では、項目をプロジェクトごとに分けて示す（`act-core:write-plan` に従う）。

## 役割はそのプロジェクトのものだけ

- 決めたプロジェクトでの操作者の役割は、個人設定の `projects.<キー>.roles` だけを使う。別のプロジェクトの役割で判定しない、書かない。
- `per_item` の項目は、それぞれ割り当てたプロジェクトの `roles` で判定する。
- 役割から書き方を決める規則は本スキルの範囲外（呼び出し元の権限判定に任せる）。

## 出力の形

```json
{
  "project_key": "FAQ",
  "rule": 2,
  "confidence": "高",
  "requires_confirmation": false,
  "reason": "入力ファイル 2 件がどちらも FAQ の root の配下",
  "candidates": [
    { "project_key": "FAQ", "reason": "root の配下（/Users/alice/共有ドライブ/faq-poc）" }
  ],
  "per_item": [
    { "item": "<呼び出し元の項目 ID かファイルの絶対パス>", "project_key": "CRM", "confidence": "中", "reason": "CRM刷新の移行日程についての記述", "scope": "meta_only" }
  ]
}
```

- `project_key`: 決めたプロジェクトのキー。決められないときは `null`。
- `rule`: 決めた規則の番号（1〜5）。決められないときは `null`。
- `confidence`: `高`／`中`／`低`。決められないときは `低`。
- `requires_confirmation`: 上の「確認を求める条件」に当たれば `true`。
- `reason`: 決めた根拠を 1 行で。呼び出し元が書き込み計画の「なぜ確認するか」に使う。
- `candidates`: 決めたときは決めたプロジェクト 1 件、決められないときは残った候補すべて。各要素に根拠を付ける。
- `per_item`（任意）: ファイルごと・項目ごとの割り当て。`scope` は `body`（本体を置く）か `meta_only`（項目だけを書く）。無ければ省略する。

## してはいけないこと

- 候補が複数残ったのに、推測や並び順で 1 つに決めない。
- 個人設定の `default_project` やセッションの選択中のプロジェクトを書き換えない（解決は読むだけで行う）。
- 個人設定に無いプロジェクト、`archived` のプロジェクトを対象にしない。
- 別のプロジェクトの役割・保存先を、決めたプロジェクトの書き込みに使わない。
