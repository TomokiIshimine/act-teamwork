# setup — 初期設定（プロジェクト参加・保存先の作成／取り込み／更新）

## 目的

1 回の実行で次の 2 つを揃える。

- 人 × プロジェクトの設定: 個人設定 `~/.act/config.yaml` の `projects` に、プロジェクトキー・役割・共有フォルダ・アカウントを 1 件追加する。
- プロジェクトの保存先: プロジェクト設定 `<root>/.act/project.yaml`、保存先の DB 一式、共通のプロジェクト一覧・クライアント・タグ、ワークフロー設定の既定を用意する。

保存先への書き込みと設定ファイルの書き込みは、すべて確認フォームでユーザーが採用した項目に限る。

## 実行前提

- 起動: `/act-core:setup [プロジェクト名] [共有フォルダのパス] [保存先のURL]`。「新しいプロジェクトに参加したい」「この Notion ページを ACT で使いたい」といった依頼から自動でも起動する。他のワークフローが個人設定の不足や保存先のスキーマ版の古さを見つけたときの案内先にもなる。
- 自動呼び出し: 許可（`disable-model-invocation` は指定しない）。根拠: 初回利用・参加・プラグイン更新後など利用者がコマンド名を知らない場面が多く、書き込みは 2 回の確認フォームを通るため、誤って起動しても承認なしに変わるものが無い。
- 引数 `$ARGUMENTS` はすべて任意。プロジェクト名・共有フォルダのパス・保存先の URL を、形から見分けて取り出す（パスは `/` や `~` で始まる、URL は `https://` で始まる、残りをプロジェクト名とする）。
- 保存先には本人の接続（Notion コネクタなど）で書く。認証情報はファイルに書かない。

## メインの作法

- ユーザーへの質問・確認はメインだけが行う。サブエージェントは質問せず、問うべき論点を出力に書く。
- サブエージェントには入力と出力先のパスを引数で渡す。サブエージェントの戻り値は、出力ファイルのパス 1 行（失敗時は `ERROR:` で始まる 1 行以上）とする。
- メインは、サブエージェントの出力ファイルを、下の「メインが読む見出し」で指定した見出しだけ読む。本文を書いたり直したりしない。
- 戻り値が `ERROR:` で始まったら次のステップに進まず、内容をユーザーに示して「失敗時の対応」に従う。
- 戻せない操作（保存先への登録・作成・変更、設定ファイルの作成・追記）の前に、内容を示してユーザーの承認を取る。本ワークフローでは Step 5 の変更計画フォームがその承認にあたり、Step 6 は承認された項目だけを適用する。
- 作業開始前に 1 回だけ `ToolSearch` を `query: "select:AskUserQuestion"`、`max_results: 1` で呼び、`AskUserQuestion` を使えるようにする。読み込めないときは、質問をチャットに番号つきの選択肢で書いて答えてもらう。
- Step 3・5 の確認フォームの組み立て（部品の選び方と、使えない環境での段の下げ方）と確信度の示し方は `act-core:write-plan` に従う。Step 3 の前に `Skill` ツールで `act-core:write-plan` を読み込む。メインとサブエージェントの間で受け渡すファイル（`02_inputs.yaml`、`04_approved-plan.json`）のキーは、本スキルの定めを正とする。
- 時間のかかるステップ（Step 4・6）の前に、何をしているかを 1 行でユーザーに伝える。

### メインが読む見出し

| 用途 | 対象ファイル | 読むところ |
| --- | --- | --- |
| Step 1 前回の実行の確認 | 前回の作業フォルダの `02_inputs.yaml` / `04_approved-plan.json` / `06_apply-result.md` | `root` キー / 各要素の `decision` / `## 結果の要約` |
| Step 3 経路の確認と基本情報フォーム | `<workdir>/01_local-state.md` | `## 判定`、`## 基本情報の推奨` |
| Step 5 変更計画フォーム | `<workdir>/03_setup-plan.md` | `## 概要`、`## 確認項目`、`## 警告` |
| Step 7 結果の報告 | `<workdir>/06_apply-result.md` | `## 結果の要約`、`## 保留した項目`、`## 警告` |

## ファイルの置き場所

- 作業フォルダ `<workdir>` は `~/.act/runs/<YYYY-MM-DD_HHMMSS>_setup/`（実行ごとに新しく作る。前回の続きから適用するときだけ前回のものを使う）。中間生成物は次のとおり。作業フォルダは削除しない（実行ログを兼ねる）。秘密情報は書かない。

| ファイル | 書く役 | 内容 |
| --- | --- | --- |
| `01_local-state.md` | `act-core:setup-local-inspector` | 経路判定、基本情報の推奨値、既存の対応づけ（参加・保存先更新） |
| `02_inputs.yaml` | メイン | 基本情報フォームの答え（キーは Step 3。Step 5 から戻るときは上書き） |
| `03_setup-plan.md` / `03_setup-plan.json` | `act-core:setup-store-planner` | 人が読む変更計画と確認項目 / 項目 ID ごとの適用内容 |
| `04_approved-plan.json` | メイン | 項目 ID ごとの採用・保留・除外と修正値（キーは Step 5） |
| `05_apply-log.jsonl` / `06_apply-result.md` | `act-core:setup-applier` | 項目ごとの適用記録 / 適用結果・保留・警告 |

- 個人設定の実体パスを `<config-path>`（絶対パス）とし、Step 2・6 に渡す。
- Claude Code では `~/.act/` と共有フォルダ `<root>` をそのまま読み書きする。`<config-path>` は `~/.act/config.yaml` を絶対パスに展開したもの。
- Cowork では `~/.act/` と `<root>` はメンバーの PC 上にあり、Step 1 で接続フォルダにする。メインとサブエージェントに渡すパスは PC 上の絶対パス（`/Users/...` など）とし、個人設定に書く `root` もこの形にする。`mcp__remote-devices__device_bash` では接続フォルダが `$HOME/mnt/<フォルダ名>` に見えるので読み替える（`device_bash` の `~` は PC のホームではない）。

## 手順

### Step 1 準備（メイン）

1. `$ARGUMENTS` からプロジェクト名・共有フォルダのパス・保存先の URL を取り出す。
2. Cowork なら、`~/.act/` を接続する。`mcp__remote-devices__get_device_info` で接続済みのフォルダを確かめ、未接続なら `mcp__remote-devices__device_list_dir` で PC のホームに `.act` があるかを見る。あれば `~/.act`（引数に共有フォルダのパスがあればそれも一緒に）を、`mcp__remote-devices__device_request_folder_access` で理由を添えて求める。無ければ、ホームフォルダ全体の接続は求めず、「ホームフォルダに `.act` という名前のフォルダを作ってから、もう一度実行する」と 1 行で案内して終える（ACT の個人設定と実行記録だけを置くフォルダで、それ以外への接続は要らないため）。
3. 共有フォルダのパスが引数に無ければ、それだけを尋ねる。背景として「プロジェクト設定 `.act/project.yaml` を置く・探す場所で、新規作成か参加かの判定に使う」を 1 文添える。
   - 候補は個人設定に登録済みの各 `root` の親フォルダ（重複は除く）。候補が 2 件以上なら `AskUserQuestion` で尋ね、各候補の説明にそのフォルダの下で登録済みのプロジェクト名を書く。自由記述でパスを直接書けることも示す。親フォルダが選ばれたら、その直下のフォルダを番号つきでチャットに示し、どれかを答えてもらう。
   - 候補が 0〜1 件（個人設定が無い初回利用を含む）なら、チャットで共有フォルダの絶対パスを 1 行で答えてもらう。候補が 1 件あれば例として示す。
   - Cowork で答えのパスが未接続なら、`device_request_folder_access` で接続を求める（Step 1 の接続の許可は最大 2 回になる）。
   - 答えを `<root>`（絶対パス）とする。接続を断られたら、何が要るかと理由を示して終える。
4. 前回の未完了の実行を探す。`~/.act/runs/*_setup/` のうち、`02_inputs.yaml` の `root` が `<root>` と同じで `04_approved-plan.json` があるものから、最も新しい 1 件だけを見る（それより古い実行は見ない）。その 1 件が次の両方に当てはまるときだけ未完了とする。
   - `04_approved-plan.json` に `decision` が `adopted` の項目が 1 件以上ある（採用 0 件で終えた実行は未完了としない）。
   - `06_apply-result.md` が無いか、`## 結果の要約` に失敗がある。

   未完了なら `AskUserQuestion` で 1 問尋ねる。背景: 前回の日時と、どこで止まったか（`## 結果の要約` の要点）。選択肢:「続きから適用する（前回承認した計画のうち、成功済みの項目を飛ばして残りを適用する）」「最初からやり直す（保存先をあらためて点検して計画を作り直す）」「中止する（何も変えずに終える）」。
   - 続きからなら、前回の作業フォルダを `<workdir>` として Step 6 に進む。中止なら終える。最初からやり直すなら手順 5 に進む。
   - 未完了でなければ、何も尋ねずに手順 5 に進む。
5. `~/.act/runs/<YYYY-MM-DD_HHMMSS>_setup/` を作り、絶対パスを `<workdir>` とする。

### Step 2 ローカル設定の点検（`act-core:setup-local-inspector`）

- 渡す引数: `root`: `<root>`、`args`: 引数のうちプロジェクト名と保存先の URL（無ければ空）、`workdir`: `<workdir>`、`config-path`: `<config-path>`
- 戻り値: `<workdir>/01_local-state.md` の絶対パス 1 行

### Step 3 基本情報フォーム（メイン）

1. `01_local-state.md` の `## 判定` と `## 基本情報の推奨` だけを読む。
2. 経路が「中止」なら、理由と次にすべきことを示して終える。
3. それ以外は、推奨値を初期値に入れた確認フォームを 1 回出す（`act-core:write-plan` の確認フォームの規定に従う）。確信度が低い値や空の値は、そのことが分かるように示す。どの経路でも「中止する（何も書かずに終える）」を選べるようにし、選ばれたら終える。経路ごとに尋ねる項目は次のとおり。
   - 新規プロジェクト作成: プロジェクト名、プロジェクトキー（候補から選ぶか自由入力）、自分の役割（`business_owner` / `manager` / `worker`、兼任可）、クライアント、保存先の場所（Notion の親ページまたは既存ページの URL）
   - 既存プロジェクトへの参加: 自分の役割。名前・キー・保存先は `project.yaml` の値を表示だけする
   - 参加済みプロジェクトの保存先更新: スキーマ版の点検に進むかの確認だけ。進まないと答えたら、何も変えずに終える
4. `<workdir>/02_inputs.yaml` に次のキーをすべて書く。フォームで尋ねなかった値・表示だけにした値は、`## 基本情報の推奨` の推奨値をそのまま書く。

| キー | 値 |
| --- | --- |
| `route` | 経路（`## 判定` の経路名のまま） |
| `root` | `<root>` |
| `project_name` | プロジェクト名 |
| `project_key` | プロジェクトキー |
| `roles` | 自分の役割の配列（`business_owner` / `manager` / `worker`） |
| `client` | クライアント名（無ければ空） |
| `store_type` | 保存先の種類（例 `notion`。フォームでは尋ねない） |
| `store_location` | 保存先の場所（URL、または `project.yaml` の `stores` の DB 識別子） |
| `shared_choice` | 共通 DB の候補を選んだときだけ、その候補の場所（Step 5 で書く。Step 3 では書かない） |

### Step 4 変更計画の作成（`act-core:setup-store-planner`）

- 起動前にユーザーへ「保存先を点検して変更計画を作っています（まだ何も書き込みません）」と伝える。
- 渡す引数: `local-state-path`: `<workdir>/01_local-state.md`、`inputs-path`: `<workdir>/02_inputs.yaml`、`workdir`: `<workdir>`
- 戻り値: `<workdir>/03_setup-plan.md` の絶対パス 1 行（同時に `<workdir>/03_setup-plan.json` が書かれる）
- このサブエージェントは保存先を読むだけで、何も変更しない。計画を作れない場合（作成者の制限、アダプタが無い、版が新しい等）は `## 概要` の先頭行が `判定: 中止` になる。

### Step 5 変更計画フォーム（メイン）

1. `03_setup-plan.md` の `## 概要`、`## 確認項目`、`## 警告` だけを読む。
2. `## 概要` の先頭行が `判定: 中止` なら、理由と次にすべきこと（マネージャーに作成を依頼する、プラグインを更新する、アダプタを入れる等）と `## 警告` を示して終える。
3. `## 確認項目` が 0 件なら、フォームを出さずに `## 概要` と `## 警告`（スキーマ版が古いので管理者に更新を依頼する、など）を示して終える。
4. それ以外は、確認フォームを 1 回出す（`act-core:write-plan` の規定に従う）。
   - `## 確認項目` の並び・各項目の確認要否・推奨の採否をそのまま使う。確認が要らず推奨が採用の項目は採用済みで示し、「すべて採用」でまとめて確定できるようにする。
   - 各項目で採用・保留・除外と、短い修正を受け付ける。
   - フォーム全体で「中止する（何も書かずに終える）」を選べるようにする。
5. 答えに応じて次のどれか 1 つを行う（上から順に当てはまるものを選ぶ）。
   - 中止が選ばれたら、何も書かずに終える。
   - プロジェクトキー・クライアント・保存先の場所を変える修正、または共通 DB の候補の選択（項目「共通 DB の候補が複数ある」の答え）があれば、適用の確認は尋ねずに「この修正で保存先を点検し直し、変更計画を作り直します」と 1 行伝え、`02_inputs.yaml` の該当キー（共通 DB の候補は `shared_choice`）を上書きして Step 4 に戻る。この往復は修正が無くなるまで続ける（上限は設けない。各回のフォームで中止を選べる）。
   - ほかの修正があれば、修正後の値を表で示し、`AskUserQuestion` で「この内容で適用する／直す／中止する」を 1 問尋ねる。「直す」ならフォームに戻り、「中止する」なら何も書かずに終える。
   - 修正が無ければ、採用・保留・除外の件数を示して確定する（追加の質問はしない）。
6. 確定した計画で分岐する。
   - 採用が 0 件なら、全項目を `held` か `excluded` として `<workdir>/04_approved-plan.json` に書き、「何も適用していない。保留した項目は `/act-core:setup` を再実行すると変更計画に再び載る」と伝えて終える（この実行は次回の Step 1 手順 4 で未完了とは見なされない）。
   - それ以外は `<workdir>/04_approved-plan.json` を書いて Step 6 に進む。
7. `04_approved-plan.json` は `{"items": [...]}` とし、`## 確認項目` の全項目について次のキーを持つ要素を 1 つずつ入れる。

| キー | 値 |
| --- | --- |
| `item_id` | `## 確認項目` の項目 ID（`03_setup-plan.json` の `item_id` と同じ） |
| `decision` | `adopted`（採用）／`held`（保留）／`excluded`（除外） |
| `override` | 修正値（無ければ `null`） |

### Step 6 適用（`act-core:setup-applier`）

- 起動前にユーザーへ「承認された N 件を保存先と設定ファイルに適用しています」と伝える（続きからの適用なら、その旨も添える）。
- 渡す引数: `plan-json-path`: `<workdir>/03_setup-plan.json`、`approved-plan-path`: `<workdir>/04_approved-plan.json`、`workdir`: `<workdir>`、`config-path`: `<config-path>`
- 戻り値: `<workdir>/06_apply-result.md` の絶対パス 1 行
- このサブエージェントは採用された項目だけを冪等に適用する。同じ作業フォルダで成功済みの項目は飛ばす。途中で失敗したら、適用済みの範囲を記録して止まる。

### Step 7 結果の報告（メイン）

1. `06_apply-result.md` の `## 結果の要約`、`## 保留した項目`、`## 警告` だけを読む。
2. ユーザーに次を示す。
   - 適用結果（成功・失敗・飛ばした件数）
   - 保留した項目と、採用するには `/act-core:setup` を再実行して変更計画フォームで採用すること（再実行すると、適用していない項目は計画に再び載る）
   - 警告（保存先のスキーマ版が古い、個人設定と保存先のメンバー登録の役割の食い違い、手作業が必要な設定の手順など）
   - 失敗があれば、原因を取り除いてから `/act-core:setup <共有フォルダのパス>` を再実行すると、Step 1 で「続きから適用する」を選べること
   - 作業フォルダ `<workdir>` の絶対パス

## 失敗時の対応

- Step 2・4・6 の戻り値が `ERROR:` で始まったら、次のステップに進まず、内容をユーザーにそのまま示して終える。入力（共有フォルダのパス、保存先の URL、基本情報）の見直しを促し、直したうえで `/act-core:setup` を再実行するよう案内する。
- Step 6 が途中で止まった場合（`06_apply-result.md` に失敗がある場合）は Step 7 で報告する。再実行すると Step 1 の手順 4 がその作業フォルダを見つけ、続きから適用するかを尋ねる。
- 必要なスキル（`act-core:write-plan`、`act-core:store-protocol`）やアダプタが読み込めない場合は、何も書かずに、足りないものを示して終える。
