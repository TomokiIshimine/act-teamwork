# ナレッジのタグの付け方

`knowledge` 候補にタグを付けるときの規則。タグは全プロジェクト共通のタグ一覧（型 `tag`）にあるものだけを付け、自由入力しない。タグ一覧は `act-core:store-protocol` の `query`（`type: tag`、名前・別名で絞る）で読む。

## タグの軸と付ける数

| 軸 | 名前の形 | 1 件に付ける数 | 付け方 |
| --- | --- | --- | --- |
| プロジェクト | `プロジェクト:<案件名>` | `プロジェクト:`・`クライアント:`・`汎用` のどれか 1 つ以上が必須 | そのプロジェクトに関わる知識。名前は共通のプロジェクト一覧の正式名 |
| クライアント | `クライアント:<会社名>` | 同上（プロジェクトと両方付けてよい） | そのクライアントに関わる知識（決算期、繁忙期、重視すること、担当者の好みなど）。案件が終わっても引けるようにする |
| 汎用 | `汎用` | 同上 | 特定のプロジェクト・クライアントに依らない知見（技術知見、教訓、方法） |
| 種類 | `種類:<値>` | 1〜2 個 | 値は固定: 事実／前提／背景・顧客理解／判断理由／方法／教訓／技術知見 |
| 話題 | `話題:<一般名詞>` | 0〜2 個 | 既存のタグから選ぶ。合うものが無ければ下の作成ルールで新しく作る案を出す |

細かい条件（データの種類、適用条件など）はタグにせず、ナレッジの `applies_to` か本文に書く。

## 付ける手順

1. **範囲のタグ**: 既定は対象プロジェクトの `プロジェクト:` タグ。内容がクライアントについての知識なら `クライアント:` タグも付ける。タグ一覧にそのプロジェクト・クライアントのタグが無ければ作らずに `warnings` に書く（作るのは初期設定の役目）。
2. **`汎用` にする案**: 内容が案件に依らないと読めても、既定ではプロジェクト・クライアントのタグを付ける。`汎用` にする案は、案件名・顧客名・個人情報を本文から除いた版を添えた別の推定値（確信度 中以下）として `estimates` に書く。`汎用` 化は所有者が確認して決める（`act-core:write-plan` で確認が要る更新）。
3. **`種類:`**: 固定の値から 1〜2 個選ぶ。
4. **`話題:`**: 本文の言葉を、タグ一覧の名前と `aliases`（別名・表記ゆれ）に照合して選ぶ。表記ゆれ・上位／下位の関係にあるタグがあればそれを使う。迷ったら広い方を選ぶ。
5. **非推奨のタグ**: 一覧で状態が `非推奨` のタグに当たったら、`merged_into`（統合先）のタグに読み替えて付ける。非推奨のタグは新しく付けない。
6. **確信度**: 推定したタグごとに `estimates` に確信度と根拠を書く。範囲のタグが対象プロジェクトから決まるものは 高、内容から推定した `種類:`・`話題:` は根拠に応じて 高〜中。

## 粒度（タグにしないもの）

| 軸 | 粒度 | タグにしないもの |
| --- | --- | --- |
| クライアント | 会社（法人）単位。グループ会社は別の会社。社内案件は自社名 | 部署、担当者、拠点 |
| プロジェクト | 案件（契約・目的のまとまり）単位。共通のプロジェクト一覧と 1 対 1 | フェーズ、工程、スプリント |
| 話題 | 別の案件でも使う一般的な言葉（PDF、検索、スケジュール、見積もり、セキュリティなど）。目安は将来 3 件以上のナレッジに付きそうなもの | 案件固有の用語、製品の型番、1 回しか出ない言葉 |

## 新しい `話題:` タグの作成ルール

新しいタグは、次のルールへの適合を示した案として `new_tags` に出す。書き込み計画では確信度にかかわらず確認が要る別の項目になる（`act-core:write-plan`）。

| # | ルール | 案での示し方 |
| --- | --- | --- |
| R1 | タグは削除しない。不要なタグは非推奨にして統合先を入れる（マネージャーの操作） | 削除の案を出さない |
| R2 | 作る前に名前と別名で既存のタグを探し、近いものがあればそれを使う。言葉を別名に足すのは誰でもできる | 探した語と、近いタグが無かった理由を書く。近いタグがあれば作らずに `alias_additions` に別名の追加案を出す |
| R3 | 名前は `話題:<値>`。値は別の案件でも使う一般名詞で、上の「タグにしないもの」に当たらない | 一般名詞である理由を 1 行で書く |
| R4 | `definition`（何に付けるか、付けない例、似たタグとの違い）を必ず書く | `definition` を埋める |
| R5 | 作ったら同じ実行で 1 件以上のナレッジに付ける。使う予定だけのタグは作らない | そのタグを付ける `knowledge` 候補の `cand_id` を `used_by` に書く。ナレッジ候補側は `depends_on` にタグの `cand_id` を書く |
| R6 | 利用者が作れるのは `話題:` だけ。`種類:` は固定、`プロジェクト:`・`クライアント:` は初期設定で作る | `話題:` 以外の案を出さない |
| R7 | 既存のタグの改名・非推奨化・統合先の設定・軸の変更はマネージャーだけ | 改名などが要りそうなときは案にせず `warnings` に書く |

### `new_tags` の形

```json
{
  "cand_id": "t-1",
  "name": "話題:表の前処理",
  "axis": "話題",
  "aliases": "表の抽出, テーブル変換",
  "definition": "何に付けるか / 付けない例 / 似たタグとの違い",
  "rule_check": { "R2": "『表』『テーブル』で探し、近いのは 話題:PDF だけ（範囲が広すぎる）", "R3": "別の案件でも使う一般名詞" },
  "used_by": ["c-3"]
}
```

### `alias_additions` の形

```json
{ "tag": "話題:スケジュール", "add": "日程", "basis": "本文の『日程』が既存のタグと同じ意味", "used_by": ["c-5"] }
```
