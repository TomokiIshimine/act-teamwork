# setup — 初期設定（プロジェクト参加・保存先の作成／取り込み／更新）

## 目的

1 回の実行で次の 2 つを揃える。

- 人 × プロジェクトの設定: 個人設定 `~/.act/config.yaml` の `projects` に、プロジェクトキー・役割・共有フォルダ・アカウントを 1 件追加する。
- プロジェクトの保存先: プロジェクト設定 `<root>/.act/project.yaml`、保存先の DB 一式（実行ログを含む）、プロジェクトのトップページ（概要と現在の状況の雛形）、共通のプロジェクト一覧・クライアント・タグ、ワークフロー設定の既定を用意する。

保存先への書き込みと設定ファイルの書き込みは、すべて変更計画フォーム（Step 5）でユーザーが採用した項目に限る。

## 実行前提

- 起動: `/act-core:setup [プロジェクト名] [共有フォルダのパス] [保存先のURL]`。「新しいプロジェクトに参加したい」「この Notion ページを ACT で使いたい」といった依頼から自動でも起動する。他のワークフローが個人設定の不足や保存先のスキーマ版の古さを見つけたときの案内先にもなる。
- 引数 `$ARGUMENTS` はすべて任意。プロジェクト名・共有フォルダのパス・保存先の URL を、形から見分けて取り出す（パスは `/` や `~` で始まる、URL は `https://` で始まる、残りをプロジェクト名とする）。
- 保存先には本人の接続（Notion コネクタなど）で書く。認証情報はファイルに書かない。

## メインの作法

act-core は他のプラグインのスキルに依存しないため、メインの作法を本節に自己完結で書く。

- ユーザーへの質問・確認はメインだけが行う。サブエージェントは質問せず、問うべき論点を出力に書く。
- サブエージェントには入力と出力先のパスを引数で渡す。サブエージェントの戻り値は、出力ファイルのパス 1 行（失敗時は `ERROR:` で始まる 1 行以上）とする。
- メインは、サブエージェントの出力ファイルを、下の「メインが読む見出し」で指定した見出しだけ読む。本文を書いたり直したりしない。
- 戻り値が `ERROR:` で始まったときの扱いは「失敗時の対応」に従う。
- 戻せない操作（保存先への登録・作成・変更、設定ファイルの作成・追記）の前に、内容を示してユーザーの承認を取る。本ワークフローでは Step 5 の変更計画フォームがその承認にあたり、Step 6 は承認された項目だけを適用する。
- 作業開始前に `Skill` ツールで `act-core:write-plan` を読む。当てる節は Step ごとに次のとおりとする。
  - Step 1・3 の質問: 「部品の選び方」（段と段の下げ方）と、「確認フォームの組み立て」のうち「推奨を初期値に入れる」だけ。「まとめて答えられるようにする」「一度に出す質問は 5 問まで」などほかの規定は当てない。値を 1 つずつ集める聞き取りで、書き込み計画の確認ではないため。確信度の示し方は Step 3 手順 5 の定めによる。
  - Step 5 の変更計画フォーム: 「確認フォームの組み立て」（「部品の選び方」を含む）と「答えの反映」。
- 作業開始前に 1 回だけ `ToolSearch` を `query: "select:AskUserQuestion"`、`max_results: 1` で呼び、`AskUserQuestion` を使えるようにする。読み込めないときは、`act-core:write-plan` の「部品の選び方」の段の下げ方に従って下の段で尋ねる。
- 作業開始前に `Skill` ツールで `act-core:local-files` を読む。メインが読み書きする設定ファイルと作業フォルダ（Step 1 の前回の実行の確認、`02_inputs.yaml`・`04_approved-plan.json` の書き込みなど）は、これに従う。
- メインとサブエージェントの間で受け渡すファイル（`02_inputs.yaml`、`04_approved-plan.json`）のキーは、本スキルの定めを正とする。
- 作業開始前に `Skill` ツールで `act-core:setup-fields` を読む。Step 1・3 でユーザーに示す説明（質問に添える文、入力の条件と例、経路の意味、確定値の一覧の「何に使われるか」、役割ごとにできること、保存先更新の経路でのスキーマ版と保存先の更新の説明）は、その文を使う。本スキルは、どの説明をいつ・どの順で示すかだけを定め、説明文を書かない。
- 時間のかかるステップ（Step 3 からの Step 2 の再実行、Step 4・6）の前に、何をしているかを 1 行でユーザーに伝える。

### メインが読む見出し

| 用途 | 対象ファイル | 読むところ |
| --- | --- | --- |
| Step 1 前回の実行の確認 | 前回の作業フォルダの `02_inputs.yaml` / `04_approved-plan.json` / `06_apply-result.md` | `root` キー / 各要素の `decision` / `## 結果の要約`（先頭行の `状態: 完了` か `状態: 停止（段 <N>）` と要点） |
| Step 3 経路の確認と基本情報の聞き取り（参加・保存先更新ではスキーマ版の記録、保存先更新では役割と `root` の更新も使う） | `<workdir>/01_local-state.md` | `## 判定`（先頭行の `経路: <経路名>`、理由、「`root` の更新:」の行）、`## 基本情報の推奨`（「スキーマ版（記録）」の行を含む）。Step 3 で Step 2 を再実行したときは読み直す |
| Step 5 変更計画フォーム | `<workdir>/03_setup-plan.md` / `<workdir>/03_setup-plan.json` | `## 概要`、`## 確認項目`、`## 警告` / `items` の各要素の `item_id`・`kind`・`replan_key` |
| Step 7 結果の報告 | `<workdir>/06_apply-result.md` | `## 結果の要約`、`## 保留した項目`、`## 警告` |

## ファイルの置き場所

- 作業フォルダ `<workdir>` は `~/.act/runs/<YYYY-MM-DD_HHMMSS>_setup/`。実行ごとに新しく作る。前回の続きから適用するときだけ前回のものを使う。
- 作業フォルダは削除しない。実行者の手元の詳細な記録と、続きから適用するときの起点になるため。
- チームで共有する実行の記録は、Step 6 で `act-core:setup-applier` が保存先の実行ログに 1 行残す（run_id＝作業フォルダ名で対応する）。
- 作業フォルダには秘密情報を書かない。
- 中間生成物は次の表のとおり。

| ファイル | 書く役 | 内容 |
| --- | --- | --- |
| `01_local-state.md` | `act-core:setup-local-inspector` | 経路判定、基本情報の推奨値、記録されたスキーマ版、既存の対応づけ（参加・保存先更新） |
| `02_inputs.yaml` | メイン | 基本情報の聞き取りの答え（キーは Step 3。Step 5 から戻るときは上書き） |
| `03_setup-plan.md` / `03_setup-plan.json` | `act-core:setup-store-planner` | 人が読む変更計画と確認項目 / 項目 ID ごとの適用内容（形は下の `### 03_setup-plan.json の形`） |
| `04_approved-plan.json` | メイン | 項目 ID ごとの採用・保留・除外と修正値（キーは Step 5） |
| `05_apply-log.jsonl` / `06_apply-result.md` | `act-core:setup-applier` | 項目ごとの適用記録 / 適用結果・保留・警告 |

- 個人設定の実体パスを `<config-path>`（絶対パス）とし、Step 2・6 に渡す。
- Claude Code では `~/.act/` と共有フォルダ `<root>` をそのまま読み書きする。`<config-path>` は `~/.act/config.yaml` を絶対パスに展開したもの。
- Cowork では `~/.act/` と `<root>` はメンバーの PC 上にあり、Step 1 で接続フォルダにする。メインとサブエージェントに渡すパスは PC 上の絶対パス（`/Users/...` など）とし、個人設定に書く `root` もこの形にする。読み書きの手段（接続フォルダの読み替えを含む）は、メインもサブエージェントも `act-core:local-files` に従う。

### 03_setup-plan.json の形

`act-core:setup-store-planner` が書き、メイン（Step 5）と `act-core:setup-applier`（Step 6）が読む適用用の計画。

| 最上位のキー | 値 |
| --- | --- |
| `route` | 経路（`02_inputs.yaml` の `route` と同じ値） |
| `store_type` | 保存先の種類（例 `notion`） |
| `modes` | 点検したアダプタごとのモード（例 `{"notion": "新規作成", "localfs": "変更なし"}`） |
| `target_schema_version` | 点検したアダプタごとの `describe` の `schema_version` |
| `accounts` | 書き込み前の照合に使う値。点検したアダプタごとに `{<adapter>: {"workspace": <inspect の workspace>, "user": <inspect の user の id>}}`（localfs の `workspace` は `root`） |
| `run_id` | `<workdir>` のフォルダ名 |
| `items` | 適用する項目の配列（中止の計画では空） |

| `items` の要素のキー | 値 |
| --- | --- |
| `item_id` | `03_setup-plan.md` の `## 確認項目` の項目 ID と同じ |
| `step` | 適用の段（1〜6。下の段の表） |
| `kind` | 項目の種類（例 `clear_migration`、`update_root`） |
| `requires_confirmation` | 確認が要るか（真偽） |
| `payload` | `apply` に渡す `changes` と `mapping`、`create` に渡す型とエンティティ、`project.yaml` の内容案、または個人設定 `projects` に追加する 1 件 |
| `replan_key` | この項目に修正・選択があったときに書き戻す `02_inputs.yaml` のキー（`project_key`／`client`／`store_location`／`shared_choice` のいずれか）。該当しなければ `null` |

適用の段（`act-core:setup-applier` はこの順で適用し、`05_apply-log.jsonl` の `step` にこの番号を書く。段 0 は項目を持たない）。

| 段 | 内容 |
| --- | --- |
| 0 | 接続先の照合（`inspect` の `workspace` と最上位の `accounts`。保存先には何も書かない） |
| 1 | スキーマ（止まった移行の印を外す `clear_migration` と、保存先のスキーマの `apply`） |
| 2 | 共通一覧へのプロジェクト登録、クライアント、タグ、メンバー DB への自分の登録 |
| 3 | 接続確認 |
| 4 | 適用したスキーマ版の記録 |
| 5 | ワークフロー設定（既定の登録、または別プロジェクトからのコピー） |
| 6 | `project.yaml` と個人設定（`project.yaml` の作成・`mapping` の書き込み、個人設定への 1 件追加、`root` の更新） |

個人設定に追加する 1 件の `payload` は `projects` の 1 項目の形にする: `{"<KEY>": {"name": <プロジェクト名>, "roles": [<役割>], "root": <共有フォルダのパス>, "accounts": {<store_type>: {"workspace": ..., "user": ...}}}}`。個人設定のファイルが無い（初回）ときは、`payload` に `me`（`inspect` の `user` の `name`・`email`）も入れる。

段 1 でまだ作られていない DB は、識別子の代わりに `{"store": "<型>"}` と書く（`project.yaml` の内容案の `stores`、段 2 の `create` の対象 DB など）。適用時に、段 1 で作られた DB の `store_ids` のその型の識別子に置き換える。

## 手順

### Step 1 準備（メイン）

1. `$ARGUMENTS` からプロジェクト名・共有フォルダのパス・保存先の URL を取り出す。共有フォルダのパスがあれば、`~` を展開した絶対パスにして `<root>` とする。
2. Cowork なら、`~/.act/` を接続フォルダにする（引数に共有フォルダのパスがあればそれも一緒に求める）。接続を求めるのは `~/.act` だけで、ホームフォルダ全体の接続は求めない（ACT の個人設定と実行記録だけを置くフォルダのため）。使う手段: 接続済みかの確認は `mcp__remote-devices__get_device_info`、`.act` の有無は `mcp__remote-devices__device_list_dir`、接続の依頼は `mcp__remote-devices__device_request_folder_access`（理由を添える）。
   - PC のホームに `.act` が無ければ、「ホームフォルダに `.act` という名前のフォルダを作ってから、もう一度実行する」と 1 行で案内して終える。
   - `~/.act` か引数の共有フォルダの接続を断られたら、何も書かずに、接続が要るフォルダとその理由（`~/.act` は個人設定と実行の記録を読み書きするため、共有フォルダは `act-core:setup-fields` の共有フォルダのパスの説明）を示して終える。
3. 共有フォルダのパスが引数に無ければ、それだけを尋ねる。`act-core:setup-fields` の `## 質問に添える説明` の共有フォルダのパスの文を添える。
   - 候補は個人設定に登録済みの各 `root` の親フォルダ（重複は除く）。候補が 2 件以上なら `AskUserQuestion` で尋ね、各候補の説明にそのフォルダの下で登録済みのプロジェクト名を書く。自由記述でパスを直接書けることも示す。親フォルダが選ばれたら、その直下のフォルダを番号つきでチャットに示し、どれかを答えてもらう。
   - 候補が 0〜1 件（個人設定が無い初回利用を含む）なら、チャットで共有フォルダの絶対パスを 1 行で答えてもらう。候補が 1 件あれば例として示す。
   - Cowork で答えのパスが未接続なら、`device_request_folder_access` で接続を求める（Step 1 の接続の許可は最大 2 回になる）。
   - 答えを、`~` を展開した絶対パスにして `<root>` とする。接続を断られたら、何が要るかと理由を示して終える。
4. 前回の未完了の実行を探す。`~/.act/runs/*_setup/` のうち、`02_inputs.yaml` の `root` が `<root>` と同じで `04_approved-plan.json` があるものから、最も新しい 1 件だけを見る（それより古い実行は見ない）。その 1 件が次の両方に当てはまるときだけ未完了とする。
   - `04_approved-plan.json` に `decision` が `adopted` の項目が 1 件以上ある（採用 0 件で終えた実行は未完了としない）。
   - `06_apply-result.md` が無いか、その `## 結果の要約` の先頭行が `状態: 完了` でない。

   未完了なら `AskUserQuestion` で 1 問尋ねる。背景: 前回の日時と、どこで止まったか（`## 結果の要約` の要点）。選択肢:「続きから適用する（前回承認した計画のうち、成功済みの項目を飛ばして残りを適用する）」「最初からやり直す（保存先をあらためて点検して計画を作り直す）」「中止する（何も変えずに終える）」。
   - 続きからなら、前回の作業フォルダを `<workdir>` として Step 6 に進む。中止なら終える。最初からやり直すなら手順 5 に進む。
   - 未完了でなければ、何も尋ねずに手順 5 に進む。
5. `~/.act/runs/<YYYY-MM-DD_HHMMSS>_setup/` を作り、絶対パスを `<workdir>` とする。

### Step 2 ローカル設定の点検（`act-core:setup-local-inspector`）

- 渡す引数: `root`: `<root>`、`args`: 引数のうちプロジェクト名と保存先の URL（無ければ空）、`workdir`: `<workdir>`、`config-path`: `<config-path>`
- 戻り値: `<workdir>/01_local-state.md` の絶対パス 1 行

### Step 3 基本情報の聞き取り（メイン）

1. `01_local-state.md` の `## 判定` と `## 基本情報の推奨` だけを読む。
2. `## 判定` の先頭行が `経路: 中止` なら、理由と次にすべきことを示して終える。
3. 経路ごとに、次の項目を表の順に尋ねる。

   | 経路 | 尋ねる項目（この順） |
   | --- | --- |
   | 新規プロジェクト作成 | プロジェクト名、プロジェクトキー、自分の役割、クライアント、保存先の場所（Notion の親ページまたは既存ページの URL） |
   | 既存プロジェクトへの参加 | 自分の役割だけ |
   | 参加済みプロジェクトの保存先更新 | なし（手順 7 の確認が「点検に進むか」を兼ねる） |

   - 新規プロジェクト作成では、引数で与えられたプロジェクト名・保存先の URL は尋ね直さず、その値を確定値にする。
   - 参加・保存先更新では、引数の値は使わない（`project.yaml` の値が正。食い違いは `act-core:setup-local-inspector` が `01_local-state.md` の `## 警告` に書く）。
4. 最初の質問の前に（尋ねる項目が無い経路では手順 6 の説明の前に）、次を 1〜2 行で示す。
   - 判定された経路と、その理由（`## 判定` の理由）。経路の意味は、`act-core:setup-fields` の `## 項目の一覧` の「経路」の「何に使われるか」の文を使う。
   - 参加・保存先更新では、対象のプロジェクト名（`## 基本情報の推奨` の値）。
   - これから尋ねる項目の数と順序。尋ねる項目があるときは、「どの質問でも『中止』と答えれば、何も書かずに終える」ことも、ここで 1 回だけ示す。
5. 尋ね方は次のとおり。
   - どの項目にも共通の尋ね方:
     - 1 問に 1 項目だけを尋ね、手順 3 の表の順に進める。各質問には、`act-core:setup-fields` の `## 質問に添える説明` のその項目の文を添える。
     - 推奨値・候補があれば先頭の選択肢に置き、「（推奨）」と示す。確信度が中・低なら、`## 基本情報の推奨` の理由を 1 行添える。
     - 段 1（`AskUserQuestion`）では、自由記述の選択肢（「その他」）を自分で作らない。候補以外の値を自由記述に書けることは質問文で示す。段 3（チャットの番号付き一覧）に下がったときだけ、一覧に「その他」を置く。
     - 候補の無い値（プロジェクト名、保存先の URL、候補が空のプロジェクトキー）は、Step 1 手順 3 と同じく、チャットで 1 行で答えてもらう。答えの例を、`act-core:setup-fields` の `## 自分で入力するときの条件と例` から 1 行添える。
     - 各質問には中止の選択肢を置かない。どの質問でも、答えに「中止」と書かれたら、何も書かずに終える。
   - プロジェクト名: 答えを得たら、キーを尋ねる前に Step 2 をもう一度起動する。
     - 起動の前に「この名前からプロジェクトキーの候補を作っています」と 1 行伝える。
     - 引数は Step 2 と同じにし、`args` だけを答えの名前（と引数の保存先の URL）にする。`workdir` は同じ `<workdir>` を渡す。
     - 戻り値が `ERROR:` で始まれば、「失敗時の対応」に従う。
     - 読み直した `## 判定` の先頭行が `経路: 中止` なら、理由と次にすべきことを示して終える。
     - それ以外は、読み直した `## 基本情報の推奨` のキー候補でプロジェクトキーを尋ねる。
   - プロジェクトキー: 候補があれば選択肢にし、質問文に、候補以外のキーは自由記述に書けることと、`act-core:setup-fields` の `## 自分で入力するときの条件と例` のプロジェクトキーの条件を添える。候補が空なら、`## 基本情報の推奨` の理由と同じ条件・例を添えて、チャットで 1 行で答えてもらう。
   - 役割（`business_owner` / `manager` / `worker`）: 複数選択にする（兼任可）。新規プロジェクト作成で、答えに `manager` も `business_owner` も無ければ、次の項目に進まない。
     - `act-core:setup-fields` の `## 役割の値` に従って、この役割では保存先を作れないことを示す。
     - 続けて 1 問で、「役割を選び直す」「中止する（何も書かずに終える。マネージャーに作成を頼む）」を尋ねる。選び直すなら、役割の質問に戻る。
   - クライアント: 候補が無くても `AskUserQuestion` の 1 問で尋ねる。選択肢は「クライアントなし（社内のプロジェクトなど）」と候補（あれば）にし、クライアント名は自由記述で受ける。質問文には、`act-core:setup-fields` の `## 自分で入力するときの条件と例` のクライアントの条件と例を添える。段 3 に下がったときは、「なし」と答えれば空になることを答えの例に含める。
   - 保存先の場所: 答えの URL を、`act-core:setup-fields` の `## 自分で入力するときの条件と例` の保存先の URL の条件で確かめる。合わなければ、合わない理由を添えて尋ね直す。
6. 保存先更新の経路では、確定値の一覧の前に、次の 3 点をこの順で示す。示す文は `act-core:setup-fields` の `## スキーマ版と保存先の更新` の文を使う。具体的な移行内容・版の番号は示さない（変更計画フォームで示す）。
   - (a) 今のスキーマ版: `## 基本情報の推奨` の「スキーマ版（記録）」の値に、`### スキーマ版` の説明を添える。値が空なら「`project.yaml` に記録なし」と示す。
   - (b) 更新で起きること: `### 保存先の更新` の「起きること」。
   - (c) 更新できる役割: `### 保存先の更新` の「更新できる役割」のうち、スキーマを更新できる役割の説明。
   - 役割（`## 基本情報の推奨` の役割）が `worker` だけのときは、「更新できる役割」の `worker` だけのときの説明も示す。さらに `## 判定` に「`root` の更新:」の行が無ければ、「点検しても版は上がらない」ことも示す。
7. 尋ね終えたら（尋ねる項目が無い経路ではすぐに。保存先更新の経路では手順 6 の説明の後に）、確定値の一覧を次の表で示す。
   - 列: 項目・値・何に使われるか・値の出どころ（引数／答え／推奨／`project.yaml`）。「何に使われるか」は、`act-core:setup-fields` の `## 項目の一覧` の同じ項目の「何に使われるか」の文を使う（「スキーマ版（記録）」の行は「スキーマ版」の文を使う）。
   - 行: 経路、共有フォルダのパス、プロジェクト名、プロジェクトキー、役割、クライアント、保存先の種類、保存先の場所。参加・保存先更新では「スキーマ版（記録）」の行も加える（値の出どころは `project.yaml`。表示だけで、`02_inputs.yaml` には書かない）。
   - 新規プロジェクト作成で保存先の場所を答えたときは、保存先の種類の値は、`act-core:setup-fields` の `## 項目の一覧` の「保存先の種類」に従って答えの URL から決めた値にする。

   続けて 1 問で、次の選択肢から尋ねる。質問文には、直す項目と値は自由記述にも書けることと、書き方の例（「プロジェクトキーを SALES に」）を 1 行添える。
   - 既定（新規プロジェクト作成・参加）:「この内容で進める」「直す項目がある（自由記述に項目と値を書く）」「中止する（何も書かずに終える）」
   - 保存先更新で、役割に `manager` か `business_owner` がある: 1 つ目を「スキーマ版の点検に進む」とする（ほかの 2 つは既定と同じ）。
   - 保存先更新で、役割が `worker` だけで `## 判定` に「`root` の更新:」の行がある: 1 つ目を「点検に進む（`root` の更新を変更計画に載せる）」とする（ほかの 2 つは既定と同じ）。
   - 保存先更新で、役割が `worker` だけで `## 判定` に「`root` の更新:」の行が無い: 選択肢を 2 つにする。「点検だけ行う（推奨。スキーマは変えない。点検は保存先を読むだけで、書く項目があれば変更計画フォームで確認する。版が古ければ、警告とマネージャー（`manager`）への更新の依頼を示す）」「中止する（何も書かずに終える）」。`worker` を一律には止めない。

   答えに応じて次のどれかを行う。
   - 中止なら、何も書かずに終える。
   - 直す項目があれば（「直す項目がある」が選ばれたか、自由記述に項目と値が書かれたとき）、次の表に従って扱い、一覧を出し直して同じ 1 問を尋ねる（上限なし）。「直す項目がある」だけが選ばれ、項目と値が書かれていなければ、先にチャットで 1 行で直す項目と値を尋ねる（上の書き方の例を添える）。

     | 直す項目 | 扱い |
     | --- | --- |
     | 経路、保存先の種類、スキーマ版（記録） | ここでは直せないことを示す。経路は共有フォルダの設定と個人設定から、保存先の種類は保存先の場所から決まり、スキーマ版（記録）は表示だけのため。経路を変えたいなら共有フォルダのパスを、保存先の種類を変えたいなら保存先の場所を見直すよう添える。 |
     | 共有フォルダのパス | 何も書かずに終え、正しいパスを引数にして `/act-core:setup <共有フォルダのパス>` を再実行するよう案内する（経路の判定と前回の実行の確認がこのパスで決まるため）。一覧は出し直さない。 |
     | プロジェクト名（新規プロジェクト作成） | 手順 5 のプロジェクト名の「Step 2 をもう一度起動する」からやり直し、プロジェクトキーを尋ね直す。ほかの答えは残し、キーを答えたら一覧を出し直す。 |
     | プロジェクトキー、クライアント（新規プロジェクト作成） | 値を反映する。 |
     | 保存先の場所（新規プロジェクト作成） | 手順 5 の保存先の場所の確かめ方で確かめてから反映し、保存先の種類も答えの URL から決め直す。 |
     | 役割（新規プロジェクト作成・参加） | 値を反映する。新規プロジェクト作成では、手順 5 の役割の確かめ（`manager` も `business_owner` も無いとき）も行う。 |
     | 役割（保存先更新） | 個人設定の値が正で、ここでは変えられないことを示す。変えたいときは、個人設定のこのプロジェクトの `roles` を直してから再実行するよう案内する。 |
     | プロジェクト名・プロジェクトキー・クライアント・保存先の場所（参加・保存先更新） | その値は共有設定（`project.yaml`）が正で、ここでは変えられないことと、マネージャーに確認するよう案内する。 |

   - 進めると答えたら（「スキーマ版の点検に進む」「点検に進む」「点検だけ行う」を含む）、手順 8 に進む。「点検だけ行う」でも Step 4 以降は変わらない（変更計画に役割にかかわらず載る項目があれば Step 5 で尋ね、0 件なら Step 5 手順 3 のとおり `## 概要` と `## 警告` を示して終える）。
8. `<workdir>/02_inputs.yaml` に、次のキーのうち `shared_choice` 以外をすべて書く。尋ねなかった値・表示だけにした値は、`## 基本情報の推奨` の推奨値（新規プロジェクト作成で引数から確定した値は引数の値）を書く。新規プロジェクト作成で保存先の場所を答えたときの `store_type` は、手順 7 で答えの URL から決めた値を書く。「スキーマ版（記録）」はキーに無いので書かない。

| キー | 値 |
| --- | --- |
| `route` | 経路（`## 判定` の先頭行 `経路: <経路名>` の経路名のまま） |
| `root` | `<root>` |
| `project_name` | プロジェクト名 |
| `project_key` | プロジェクトキー |
| `roles` | 自分の役割の配列（`business_owner` / `manager` / `worker`） |
| `client` | クライアント名（無ければ空） |
| `store_type` | 保存先の種類（例 `notion`。聞き取りでは尋ねない） |

### Step 4 変更計画の作成（`act-core:setup-store-planner`）

- 起動前にユーザーへ「保存先を点検して変更計画を作っています（まだ何も書き込みません）」と伝える。
- 渡す引数: `local-state-path`: `<workdir>/01_local-state.md`、`inputs-path`: `<workdir>/02_inputs.yaml`、`workdir`: `<workdir>`
- 戻り値: `<workdir>/03_setup-plan.md` の絶対パス 1 行（同時に `<workdir>/03_setup-plan.json` が書かれる）
- このサブエージェントは保存先を読むだけで、何も変更しない。計画を作れないときは `## 概要` の先頭行が `判定: 中止` になる。

### Step 5 変更計画フォーム（メイン）

1. `03_setup-plan.md` の `## 概要`、`## 確認項目`、`## 警告` だけを読む。
2. `## 概要` の先頭行が `判定: 中止` なら、理由と次にすべきこと（マネージャーに作成を依頼する、プラグインを更新する、アダプタを入れる等）と `## 警告` を示して終える。
3. `## 確認項目` が 0 件なら、フォームを出さずに `## 概要` と `## 警告`（スキーマ版が古いのでマネージャー（`manager`）に更新を依頼する、など）を示して終える。
4. それ以外は、`## 概要`（モード・件数・適用後に実行ログへ今回の実行を 1 行残すこと）と `## 警告` をユーザーに示し、同じメッセージで確認フォームを 1 回出す。`## 確認項目` の並び・各項目の確認要否・推奨の採否をそのまま使う（組み立て・中止の選択肢は `act-core:write-plan` の「確認フォームの組み立て」に従う）。各項目で採用・保留・除外と、短い修正を受け付ける。
5. 答えに応じて次のどれか 1 つを行う（上から順に当てはまるものを選ぶ）。
   - 中止が選ばれたら、何も書かずに終える。
   - `03_setup-plan.json` で `replan_key` を持つ項目に修正・選択があれば、適用の確認は尋ねずに「この修正で保存先を点検し直し、変更計画を作り直します」と 1 行伝え、`02_inputs.yaml` のその `replan_key` のキーを修正値・選択値で上書きして Step 4 に戻る。この往復は修正が無くなるまで続ける（上限は設けない。各回のフォームで中止を選べる）。
   - 項目の種類が ID の接頭辞の衝突（`kind` が `prefix_conflict`）のものが、キーの変更も取り込みも選ばれずに残ったら、何も書かずに終える。使用済みの接頭辞と使っている DB を示し、その DB を直すかキーを変えて `/act-core:setup` を再実行するよう案内する（そのまま適用すると、DB の作成が Notion に拒否されて途中で止まるため）。
   - それ以外は、`act-core:write-plan` の「答えの反映」に従って採否と修正値を確定する。確定の確認で中止が選ばれたら、何も書かずに終える。
6. 確定した計画で分岐する。
   - 採用が 0 件なら、全項目を `held` か `excluded` として `<workdir>/04_approved-plan.json` に書き、「何も適用していない。保留した項目は `/act-core:setup` を再実行すると変更計画に再び載る」と伝えて終える（この実行は次回の Step 1 手順 4 で未完了とは見なされない）。
   - それ以外は `<workdir>/04_approved-plan.json` を書いて Step 6 に進む。
7. `04_approved-plan.json` は `{"items": [...]}` とし、`## 確認項目` の全項目について次のキーを持つ要素を 1 つずつ入れる。

| キー | 値 |
| --- | --- |
| `item_id` | `## 確認項目` の項目 ID（`03_setup-plan.json` の `item_id` と同じ） |
| `decision` | `adopted`（採用）／`held`（保留）／`excluded`（除外） |
| `override` | 修正値（無ければ `null`） |

### Step 6 適用（`act-core:setup-applier`）

- 起動前にユーザーへ「承認された N 件を保存先と設定ファイルに適用しています」と伝える（続きからの適用なら、その旨も添える）。
- 渡す引数: `plan-json-path`: `<workdir>/03_setup-plan.json`、`approved-plan-path`: `<workdir>/04_approved-plan.json`、`inputs-path`: `<workdir>/02_inputs.yaml`、`workdir`: `<workdir>`、`config-path`: `<config-path>`
- 戻り値: `<workdir>/06_apply-result.md` の絶対パス 1 行
- 同じ `<workdir>` を渡すと、成功済みの項目は飛ばされる（続きからの適用はこれによる）。途中で失敗したら、適用済みの範囲を記録して止まる。
- 最後に実行ログへ今回の実行を記録する（途中で止まったときも）。実行ログへの記録は確認項目にしない（実行そのものの記録で、承認された適用の結果だけを書くため）。

### Step 7 結果の報告（メイン）

1. `06_apply-result.md` の `## 結果の要約`、`## 保留した項目`、`## 警告` だけを読む。
2. ユーザーに次を示す。
   - 適用結果（成功・失敗・飛ばした件数）
   - 保留した項目と、採用するには `/act-core:setup` を再実行して変更計画フォームで採用すること（再実行すると、適用していない項目は計画に再び載る）
   - 警告（保存先のスキーマ版が古い、個人設定と保存先のメンバー登録の役割の食い違い、手作業が必要な設定の手順など）
   - `## 結果の要約` の先頭行が `状態: 完了` でなければ、原因を取り除いてから `/act-core:setup <共有フォルダのパス>` を再実行すると、Step 1 で「続きから適用する」を選べること
   - 実行ログの行の URL（記録できなかったときはその旨。`## 結果の要約`・`## 警告` にある）
   - 作業フォルダ `<workdir>` の絶対パス

## 失敗時の対応

- Step 2（Step 3 手順 5 からの再実行を含む）・4・6 の戻り値が `ERROR:` で始まったら、次のステップに進まず、内容をユーザーにそのまま示して終える。入力（共有フォルダのパス、保存先の URL、基本情報）の見直しを促し、直したうえで `/act-core:setup` を再実行するよう案内する。
- Step 6 が途中で止まった場合（`06_apply-result.md` の `## 結果の要約` の先頭行が `状態: 停止（段 <N>）` の場合）は Step 7 で報告する。再実行すると Step 1 の手順 4 がその作業フォルダを見つけ、続きから適用するかを尋ねる。
- 作業開始前に `act-core:write-plan` か `act-core:setup-fields` を読み込めなければ、何も書かずに、足りないものを示して終える。アダプタや `act-core:store-protocol` の不足はサブエージェントが `判定: 中止`（Step 5 手順 2）か `ERROR:`（上の項目）で返す。
