# write-plan — 書き込み計画と確認フォーム

ACT のワークフローは、確信のある更新だけを、人が確認してから書く。そのために、書く前に「書き込み計画」を作り、確認フォームで採否を決めてもらい、採用された項目だけを書く。人に確認できないとき（定期実行など）は書かない。

役割の分担:

- 計画を作る役（多くはサブエージェント）: 項目を組み立て、確信度・理由・推奨を付けて、計画ファイルに書く。ユーザーには質問しない。
- 確認を取る役（ワークフローのメイン）: 計画の確認項目から確認フォームを組み立て、答えを受け取り、採否を確定する。
- 書く役: 採用された項目だけを書き、保留した項目を実行ログ（`act-core:store-protocol` の「実行ログ」の `held`）に残す。

計画ファイルの見出し・ファイル名・キーは、各ワークフローの定めを正とする。この規約は項目の中身と確認の取り方を定める。

## 項目の形

書き込み計画の 1 項目は次の値を持つ。

| 値 | 内容 |
| --- | --- |
| 項目 ID | 計画の中で一意。確認フォームの答えと適用を突き合わせる |
| 対象 | プロジェクト名と、その中での自分の役割。複数プロジェクトに書くときはプロジェクトごとに分けて並べる |
| 操作 | `追加`／`更新`／`状態の変更`／`提案`／`判断依頼`（種別 `request` のタスクを作る）／`スキップ（重複）` |
| 内容 | 何をどこに書くか。更新は変更前と変更後の差分 |
| 確信度 | `高`／`中`／`低`（下記）。項目全体の確信度は、中の値の確信度のうち最も低いもの |
| 推定した値 | 推定で埋めた値（プロジェクト、担当、期限、タグ、層、状態など）ごとの確信度と根拠 |
| 理由 | 中・低のとき、なぜ確認するかを 1 行で（推定の根拠、食い違う出典） |
| 確認の要否 | 下の「確信度にかかわらず確認が要る更新」に当たるか、確信度が中・低なら `要` |
| 推奨 | `採用`／`保留`／`除外` と、推定した値の推奨 |
| 選択肢 | 値に候補があるときの候補（プロジェクト、担当、タグ、層、状態など） |
| 出典 | 根拠にしたアーティファクトと版、スレッド |

## 確信度

| 確信度 | 基準 | 既定の推奨 |
| --- | --- | --- |
| 高 | 入力にはっきり書かれていて、解釈が 1 つに決まる | `採用` |
| 中 | 文脈から推定した。妥当だが別の読み方もありうる | `保留`。推定の根拠と推奨値を添える |
| 低 | 曖昧・矛盾がある、または必要な値が入力に無い | `保留`。値は空のまま、確認の質問にする |

- 推測で値を埋めない。分からない値は空にして確信度を低にする。
- 項目全体だけでなく、項目の中の推定した値にも確信度を付ける。フォームでは中・低の値だけを質問にする。

## 確信度にかかわらず確認が要る更新

次の項目は確信度が高くても `確認の要否: 要` にする。

- 既存の項目の上書き、状態の変更（完了、置換済み、中止など）
- 他者が記録した項目の変更
- ナレッジの `汎用` 化、閲覧の制限の変更
- 新しいタグの作成
- 保存先のスキーマの変換・削除、既存 DB との対応づけ（取り込み）
- 戻せない、または影響が広い操作（共通一覧への登録、設定ファイルの作成など）でワークフローが指定したもの

## 確認フォームの組み立て

答えはクリックで選べる形で取る。チャットに文章で答えさせない。

- **推奨を初期値に入れる。** 各項目の推奨（採用／保留／除外、推定した値）を初期値にし、ユーザーは違うところだけ直せばよいようにする。
- **選択式を基本にする。** 採否はチェックか選択肢、候補がある値は選択肢、日付は日付入力。自由記述は「修正があれば」の短い欄だけにする。
- **まとめて答えられるようにする。** 確認が要る項目（中・低、上の一覧に当たるもの）を先頭に並べる。確認が要らず推奨が採用の項目は採用済みでまとめて示し、「すべて採用」で確定できるようにする。
- **一度に出す質問は 5 問まで。** 残りは次の画面に送る。
- **理由を添える。** 中・低の項目には理由を 1 行で添える。
- **中止を選べるようにする。** フォーム全体で「中止する（何も書かずに終える）」を選べるようにする。

### 部品の選び方

実行環境で使える最上位の段を使う。個人設定の `preferences.confirm_ui` が `form` なら段 2、`chat` なら段 3 から始める（`auto` は最上位から）。使えなければ下の段に下がる。

| 段 | 部品 | 使う場面 |
| --- | --- | --- |
| 1 | 選択式の質問ツール（`AskUserQuestion`。選択肢・複数選択） | 質問が少ない（目安 4 問以下）とき |
| 2 | フォーム・確認ページ（Cowork の入力ウィジェット、回答を受け取れる Artifact ページ） | 項目が多い、表で見比べたいとき |
| 3 | チャットの番号付き一覧 | 上の部品が無いとき |

- 段 1 で選択肢が 4 つを超える値は、推奨と上位の候補を選択肢にし、残りは「その他（修正欄に書く）」にする。
- 段 3 では、項目に番号を振って推奨と一緒に一覧にし、「2, 5 を除外」「3 の担当は佐藤」「すべて採用」のように短く答えられる形にする。答えの例を 1 行添える。

## 答えの反映

- 答えを各項目に反映し、項目ごとに `採用`／`保留`／`除外` と修正値を確定する。
- 修正があったときは、反映後の計画を短く（変わった項目と件数）示し、確定の確認を 1 回だけ取る。修正が無ければ追加の質問はしない。
- 「保留」のまま確定した項目は書かない。次回の実行で同じ入力を読んだときに再び示せるよう、保留した項目を実行ログ（`act-core:store-protocol` の「実行ログ」の `held`）に残す。
- 確定した採否は、各ワークフローの定めるファイルに書き、書く役はそれだけを見て書く。

## 人に確認できないとき

定期実行や自動起動の途中など、人に確認できないときは書かない。確認が要る項目は「確認待ち」として残し、次にユーザーが開いたときに示す。個人設定の `preferences.confirm_before_write` が `on_conflict` でも、自動で書いてよいのは確信度が高く、既存の項目と衝突しない追加だけで、上の「確信度にかかわらず確認が要る更新」は自動で書かない。
