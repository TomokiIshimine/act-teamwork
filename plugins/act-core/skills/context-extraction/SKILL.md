# context-extraction — コンテキスト抽出

入力テキストから、保存先に書く候補を型ごとに取り出す。ここで決めるのは「何が書かれているか」と「その出典」まで。候補をどう書くか（確定・提案・判断依頼・書かない）は `act-core:permission-gate`、書き込み計画の項目と確認の取り方は `act-core:write-plan`、保存先の読み書きは `act-core:store-protocol` に従う。抽出では保存先に何も書かない。

## 呼び出し元が渡すもの

- 入力テキストと出典: アーティファクトの ID と版（スレッドならその URL）。議事録（型 `minutes`）から抽出するときはその ID。アーティファクトがまだ登録前なら、呼び出し元が決めた仮の識別子（ファイルのハッシュなど）。仮の識別子は、適用時に呼び出し元が実際の ID に置き換える。
- 抽出する型: 下の「候補の型」から、そのワークフローが必要とするものだけを指定する。指定の無い型は抽出しない。
- 対象プロジェクト: キー・名前・クライアント名（決め方は `act-core:project-resolution`）。
- 操作者: 対象プロジェクトでのメンバーと、保存先のアカウント（ナレッジの所有者に使う）。
- 関連の候補を探すときの保存先の情報（型ごとの adapter と `mapping`）。

## 候補の型

| 型 | 内容 | 正準モデルの型 |
| --- | --- | --- |
| `decision` | 決定（会議の合意、資料に書かれた決定） | `decision` |
| `task` | タスク・宿題・アクションアイテム | `task`（`kind` は呼び出し元が決める） |
| `knowledge` | 操作者本人の理解 | `knowledge` |
| `artifact` | 入力の中で言及された資料・成果物 | `artifact_meta` |
| `request` | 「持ち帰り」「要確認」など、誰かの判断を待つ事項 | `task`（`kind: request`） |
| `adoption` | 矛盾するナレッジのうち、あるタスクでどれを採用したかの記録 | `task` の進捗ログへの 1 行 |
| `link` | 既存のタスク・決定・ナレッジ・アーティファクトとの関連 | `link` 操作 |

## 候補の共通の形

```json
{
  "cand_id": "c-3",
  "type": "knowledge",
  "title": "…",
  "attributes": { "confidence": "仮説", "tags": ["プロジェクト:社内FAQ AI検証", "種類:技術知見", "話題:PDF"] },
  "narrative": { "content": "…", "evidence": "…", "caveats": "…" },
  "source": {
    "artifact": "FAQ-ART-12", "version": "v2", "minutes": null, "thread": null,
    "position": { "page": 3, "heading": "2.1 前提", "lines": "12-15" },
    "quote": "…（入力からそのまま 1〜2 文）"
  },
  "estimates": [
    { "field": "attributes.tags[2]", "confidence": "中", "basis": "…" }
  ],
  "flags": [],
  "existing": null
}
```

- `attributes` と `narrative` は正準モデルの項目名で書く（`act-core:store-protocol`「正準モデルの JSON」）。入力に無い値は入れない。
- `source` は全候補に必須。`artifact`・`minutes`・`thread` のうち出典に当たるものを入れる。`position` は分かる粒度（ページ・見出し・行、スレッドならメッセージ）で書き、`quote` は入力の文をそのまま引く。記録者・代理 AI 経由・使った設定の出典は呼び出し元が付ける。
- `estimates` には、推定で埋めた値ごとの確信度と根拠を書く。確信度の基準は `act-core:write-plan`「確信度」に従う。候補全体の確信度は、その中の値の確信度のうち最も低いもの。
- `flags` は下の型ごとの規則で付ける印。
- `existing` は、同じ内容の既存の項目が見つかったときにその ID を入れる。新規か更新か重複かは、呼び出し元が `act-core:write-plan`「重複・差分チェック」で決める。
- `cand_id` は 1 回の抽出の中で一意にする。ある候補を前提にする候補（タグの作成と、そのタグを付けるナレッジなど）は `depends_on` に前提の `cand_id` を書く。

抽出の結果は `{ "candidates": [...], "new_tags": [...], "alias_additions": [...], "warnings": [...] }` で返す。`new_tags`・`alias_additions` の形は `references/tagging.md`。

## 記録・理解・決定を分ける

1 つの記述から、資料（記録）・本人の理解（ナレッジ）・決定を別々の候補にする。1 つの候補に混ぜない。

- 記録: 入力そのもの、または入力で言及された資料。`artifact` 候補か、出典として扱う。
- 理解: 記述から操作者が得た知見。`knowledge` 候補にする。
- 決定: 誰かが決めたこと。`decision` 候補にする。

例: 「検索は全文検索ではなくベクトル検索で進めると合意。PDF の表は崩れるので前処理が要る」→ 決定 1 件（検索方式）、ナレッジ 1 件（PDF の表は前処理が要る）。

## 型ごとの規則

### `decision`

- 「決定した」「合意した」「〜で進める」と書かれた記述を候補にする。`content`（決定内容）・`rationale`（理由）・`scope`（適用範囲）を入力から書き、無ければ空にする。
- `status` は入れない。確定にするか提案にするかは `act-core:permission-gate` が決める。
- `layer`（`business`／`management`）は推定し、`estimates` に確信度と根拠を書く。
- 資料に書かれているだけの決定（その場の合意ではないもの）には `flags` に `記録された決定` を付ける。
- 意見か決定か分からないものは確信度 低にする。
- 既存の確定済みの決定と矛盾するときは、`flags` に `確定済みと矛盾` を付け、その決定への `link` 候補（`relation: supersedes`、確信度 中以下）を添える。置き換えるかどうかは呼び出し元と権限で決まり、抽出では決めない。

### `task`

- 宿題・アクションアイテム・「〜しておく」を候補にする。
- 担当（`assignee`）・期限（`due`）・完了条件（`done_criteria`）が入力に無ければ空にし、`flags` に `担当未定`／`期限未定`／`完了条件未定` を付ける。推測で埋めない。「来週中」のような曖昧な期限は日付にした値を確信度 中にする。
- `kind`（定義済み／補助）は決めない。既存のタスクの続きと読めるときは、そのタスクへの `link` 候補を添える。

### `knowledge`

- 操作者本人の理解として書く。他人の発言や資料から得た理解も本人のものとし、出典を付ける。所有者（`owner`）は操作者のアカウントだけにする。
- `confidence`: 資料の裏付けがあれば `仮説`、推論だけなら `推測`。`確認済み` は操作者が確認済みと明示したときだけ。
- `valid_as_of` は入力の日付（会議日・資料の日付）。`applies_to` には適用範囲のキーワード（データ・条件など）を短く書く。
- `content`（内容）・`evidence`（根拠）・`caveats`（注意点・適用しない条件）を書く。
- タグは `references/tagging.md` に従って付ける。
- 他者のナレッジは更新の候補にしない。他者のナレッジと食い違うときは、本人の新しいナレッジの候補にし、`flags` に `他者のナレッジと食い違い` を付けて、そのナレッジへの `link` 候補を添える（統合しない）。
- 操作者自身の既存のナレッジと同じ内容なら `existing` にその ID を入れる。

### `request`

- 「持ち帰り」「要確認」「〜さんに確認する」など、判断を待つ事項を候補にする。決定を伴わない単なる確認は候補にせず、関係する項目へのコメントの案として `warnings` に書く。
- `to_role`（`manager`／`business_owner`）は推定して確信度を付ける。`request`（何を決めてほしいか）・`background`・`options`（選択肢があれば）を入力から書く。
- 権限が足りない決定を判断依頼に切り替えるのは `act-core:permission-gate` の役目で、ここでは扱わない。

### `artifact`

- 入力の中で名前・所在が言及された資料を候補にする（入力そのものは候補にしない。入力の登録は呼び出し元のワークフローが行う）。
- `title`・推定した `kind`・言及された所在を書く。既存のアーティファクトに当たれば `existing` にその ID を入れ、`link` 候補を添える。

### `adoption`

- 入力から「矛盾するナレッジのうち、あるタスクでどれを採用したか」が読み取れたときに候補にする。
- 対象のタスク、採用したナレッジ ID、不採用の ID、観点、理由を持ち、進捗ログの 1 行を `採用: <ID> ／ 不採用: <ID> ／ 観点: <専門性・根拠など> ／ 理由: <1 文>` の形で作る。採用したナレッジをそのタスクの `related_knowledge` に結ぶ `link` 候補を添える。
- 記録するかどうか（プロジェクト設定 `policy.adoption_record`）は呼び出し元が決める。

### `link`

- 形: `{ "from", "to", "relation", "basis" }`。`relation` は `from` 側の正準の属性名（アーティファクトの `related_tasks`・`related_decisions`・`related_knowledge`、決定の `supersedes`、タスクの `related_decisions`、決定・タスクの `source_minutes`（議事録から作った候補を出典の議事録に結ぶ）など）。ナレッジの根拠のアーティファクトは、アーティファクト側の `related_knowledge` から張る。
- 確信度: 入力に ID・URL がある → 高。名前・別名・キーワードの一致だけ → 中。弱い一致は候補にせず、`warnings` にも書かない。

## 関連の候補の探し方

- 既存のタスク・決定・ナレッジ・アーティファクトを `act-core:store-protocol` の `query`（キーワード・名前・別名、関連 ID）で探す。`query` は属性だけを返すので、内容の照合が要るときだけ `get` で本文を取る。
- 探す範囲は対象プロジェクトだけにする。ナレッジは全プロジェクト共通なので、対象プロジェクト・クライアントのタグで絞る。別のプロジェクトの項目は関連の候補にしない（持ち出しは参照リンクに留める）。
- 一致の根拠（一致した語、ID の言及）を `basis` に書く。

## してはいけないこと

- 保存先に書かない。抽出は読むだけで、書き込みは書き込み計画の承認後に呼び出し元が行う。
- 入力に無い値を推測で埋めない。分からない値は空にして確信度を低にする。
- 決定の状態・タスクの種別・書き方（確定か提案か）を抽出で決めない。
- 他者のナレッジを更新・統合する候補を作らない。
- 出典の無い候補を返さない。
