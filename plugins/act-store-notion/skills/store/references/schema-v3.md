# Notion スキーマ 版 3

`act-store-notion:store` が作成・照合する Notion の構成。`describe` の `schema_version` は `3`。版 2 の定義は `schema-v2.md`、版 1 は `schema-v1.md`。

## 版 2 からの差分

- 📝 議事録 DB（型 `minutes`、プロジェクト DB、ID の接頭辞 `<KEY>-MTG`）を追加した。
- 🗂 決定事項・✅ タスクに「出典議事録」（📝 の「決定事項」「タスク」と双方向）を追加した。
- 📄 アーティファクトの種類「議事録」の扱いを変えた（下記「プロパティ」の 📄 の注記）。
- 共通 DB の構成は変えない（印の版だけ `notion/3`）。

## 全体の構成

```
<親ページ>（inspect の location に渡されたページ）
├── 🏢 クライアント        共通 DB（同じワークスペースで 1 つ）
├── 📁 プロジェクト        共通 DB
├── 🏷 タグ                共通 DB
├── 🧠 ナレッジ            共通 DB
└── ACT: <プロジェクト名>  プロジェクトのトップページ（プロジェクトごとに 1 つ）
    ├── 📌 プロジェクト概要  本文のセクション（DB ではない）
    ├── 📍 現在の状況        本文のセクション（DB ではない）
    ├── 👥 メンバー
    ├── 🗂 決定事項
    ├── ✅ タスク
    ├── 📄 アーティファクト
    ├── 📝 議事録
    ├── ⚙️ ワークフロー設定
    ├── 📰 デイリーサマリー
    ├── 🧾 実行ログ
    └── 🔧 ACT 設定          子ページ（ACT が読み書きする設定）
```

- 共通 DB は、同じワークスペースに既にあれば作らずにつなぐ（`inspect` の `shared` で見つけたもの）。共通 DB を置く場所は、最初に作ったときの親ページ。
- `[ACT]` 印の無い既存の共通 DB（手で作った保存例など）は、この定義と照合して取り込める（`inspect` の `shared.adoptable`）。取り込むと説明文の 1 行目に印を書き、足りないプロパティを足す。既存のプロパティ名・ID の接頭辞は変えない。
- プロジェクトの DB 一式は、プロジェクトのトップページの下に作る。トップページが無ければ親ページの下に `ACT: <プロジェクト名>` を、下記「トップページの雛形」の本文で作る。
- 版 1 から移した保存先では、トップページの下に `旧_📨 判断依頼`・`旧_🔎 採用記録` が退役の印付きで残る。ACT の管理外とする。

## ACT の印（マーカー）

ACT が管理する DB とページは、次の印で見分ける。

- **DB の説明文の 1 行目**: `[ACT] type=<型> schema=notion/<版>`（例: `[ACT] type=minutes schema=notion/3`）。2 行目以降は人向けの説明（作成ルールなど）を書いてよい。共通 DB の版はこの印で表す。
- **🔧 ACT 設定（トップページの子ページ）**: 本文の 1 行目は「ACT が読み書きする設定。手で編集しない」。その下のコードブロック（言語 `json`）に次を書く。プロジェクト側の版の正はこの `schema` だけ（DB の印の版では判定しない）。

  ```json
  { "schema": "notion/3", "project_key": "FAQ", "store_ids": { "task": "<データソースID>", "...": "..." }, "migrating": false, "migrating_since": null, "run_id": null }
  ```

  新規作成・取り込みでは、`apply` は始めにこのページを `schema` 空で作り、全部の変更が成功したときだけ `schema` を書く。`schema` が空の 🔧 ACT 設定は「適用途中」を表す。ページ名は絵文字を除いた「ACT 設定」で照合する。版 1 の保存先では、同じ JSON がトップページの本文の見出し `ACT 設定` の下にある（`schema-v1.md`）。版 1 から移すときは、このページを始めには作らず、`schema-v2.md` の版 1 → 2 の移行手順の C-1 で本文の JSON を写して作る。
- **ACT 設定の正**: 子ページ 🔧 ACT 設定と本文の `ACT 設定` の両方があるときは、版 1 → 2 の C-1 が終わっていないので本文を正とする（子ページは読まない。書くのは C-1 の写しだけ）。本文が無ければ子ページを正とする。
- **移行中の印**: 移行中は、正の ACT 設定（上記）の `migrating` を `true` にし、`migrating_since`（日時）と `run_id` を書く。版 1 の保存先では版 1 → 2 の C-1 までは本文の `ACT 設定` に付け、C-1 で子ページに写した後は 🔧 ACT 設定に付ける。共通 DB を変えているときは、その DB の説明文の 1 行目の末尾に ` migrating <run_id> <日時>` を付ける。終わったら（失敗で止まっても）外す。処理が切れて残った印は `clear_migration` で外す。
- **実行の記録**: 実行の記録は呼び出し元が 🧾 実行ログ に残す。アダプタは書かない。
- **退役の印**: ACT の管理から外した DB は、説明文の 1 行目を `[ACT-retired] type=<型> schema=notion/<版>` にする（`<版>` は退役させた移行の版。例: `[ACT-retired] type=request schema=notion/2`）。`inspect` は退役の印の DB を `store_ids` にも `databases` の候補にも入れない。

## 型と DB の対応

| 型（`store_ids` のキー） | DB 名 | 置き場所 | ID の接頭辞 |
| --- | --- | --- | --- |
| `client` | 🏢 クライアント | 共通 | `CLI` |
| `project_registry` | 📁 プロジェクト | 共通 | なし |
| `tag` | 🏷 タグ | 共通 | `TAG` |
| `knowledge` | 🧠 ナレッジ | 共通 | `KNW` |
| `membership` | 👥 メンバー | プロジェクト | なし |
| `decision` | 🗂 決定事項 | プロジェクト | `<KEY>-DEC` |
| `task` | ✅ タスク | プロジェクト | `<KEY>-TSK` |
| `artifact_meta` | 📄 アーティファクト | プロジェクト | `<KEY>-ART` |
| `minutes` | 📝 議事録 | プロジェクト | `<KEY>-MTG` |

| `daily_summary` | 📰 デイリーサマリー | プロジェクト | `<KEY>-SUM` |
| `run_log` | 🧾 実行ログ | プロジェクト | なし（タイトルを run_id にする） |

`<KEY>` はプロジェクトキー。Notion の ID の接頭辞はワークスペース内で一意でなければならない（同じ接頭辞の DB は作れない。ゴミ箱の DB も使用済みに数えられることがある）。そのため同じワークスペースに共通 DB は 1 組だけ置き、プロジェクトキーはワークスペース内で重ならないものにする。ID の接頭辞はこの表を正とする（要件定義書 §6.2 の `id_prefix` の既定もこの表に合わせてある）。`project.yaml` の `stores.project_registry` は `{ "projects": 📁, "clients": 🏢, "tags": 🏷 }` の 3 つの識別子を持つので、`store_ids` でも `project_registry` は `{ "projects": ..., "clients": ..., "tags": ... }` の形で返す。

## プロパティ

型の略記: `title` タイトル、`text` テキスト、`select` セレクト、`multi` マルチセレクト、`date` 日付、`person` ユーザー（Person）、`rel(<DB>)` リレーション、`check` チェックボックス、`num` 数値、`url` URL、`uid` ID（接頭辞付きの一意 ID）、`rollup` ロールアップ、`created` 作成日時、`edited` 最終更新日時。リレーションは注記が無ければ片方向。

人を指す項目は 👥 メンバー へのリレーションにする（Notion アカウントの無い人も扱える）。権限ルールに使う項目だけ `person` にする。

### 共通 DB

**🏢 クライアント**: 名前 `title`、ID `uid`、状態 `select`（取引中／終了）

**📁 プロジェクト**: 名前 `title`、プロジェクトキー `text`、状態 `select`（準備中／進行中／完了／中止）、クライアント `rel(🏢)`、トップページ `url`、閲覧グループ `person`

**🏷 タグ**: タグ `title`、ID `uid`、軸 `select`（プロジェクト／クライアント／汎用／種類／話題）、状態 `select`（有効／非推奨）、別名 `text`、統合先 `rel(🏷 自己)`、プロジェクト `rel(📁)`、クライアント `rel(🏢)`、ナレッジ `rel(🧠)`（🧠 タグと双方向）、使用件数 `rollup`（ナレッジの件数）、作成者 `person`、作成日 `created`、更新日時 `edited`
- 説明文の 2 行目以降に作成ルール（削除禁止、作る前に別名で探す、`軸:値`、定義を書く、作ったら 1 件以上に付ける、利用者が作れるのは `話題:` だけ、改名・非推奨はマネージャー）を書く。
- 作成時に `種類:` の 7 件（事実／前提／背景・顧客理解／判断理由／方法／教訓／技術知見）と `汎用` を登録する（版 1 から同じ）。

**🧠 ナレッジ**: ナレッジ `title`、ID `uid`、所有者 `person`、タグ `rel(🏷)`（双方向）、閲覧範囲 `person`、確認状態 `select`（確認済み／仮説／推測）、時点 `date`、適用範囲 `text`、代理AI経由 `check`

### プロジェクト DB

全 DB に共通して、記録者 `rel(👥)`、代理AI経由 `check` を持つ（👥 メンバー、⚙️ ワークフロー設定、📰 デイリーサマリー、🧾 実行ログ は除く。📝 議事録は含む）。

**👥 メンバー**: 名前 `title`、アカウント `person`、役割 `multi`（business_owner／manager／worker）

**🗂 決定事項**: 決定 `title`、ID `uid`、層 `select`（business／management）、状態 `select`（提案／確定／置換済み／取消）、決定者 `rel(👥)`、決定日 `date`、有効日 `date`、置き換える決定 `rel(🗂 自己、双方向)`、出典アーティファクト `rel(📄)`、出典議事録 `rel(📝、双方向。📝 側は 決定事項)`、制約を受けるタスク `rel(✅)`

**✅ タスク**: タスク名 `title`、ID `uid`、種別 `select`（defined／auxiliary／request）、状態 `select`（todo／in_progress／blocked／in_review／done／cancelled）、優先度 `select`（高／中／低）、期限 `date`、状況更新日 `date`、担当 `rel(👥)`、定義者 `rel(👥)`、親タスク `rel(✅ 自己、双方向)`、入力 `rel(📄)`、成果物 `rel(📄)`、関連する決定 `rel(🗂)`、関連ナレッジ `rel(🧠)`、出典議事録 `rel(📝、双方向。📝 側は タスク)`、宛先の役割 `select`（manager／business_owner）、判断の結果 `select`（承認／却下）、影響するタスク `rel(✅ 自己)`

**📄 アーティファクト**: 名称 `title`、ID `uid`、種類 `select`（議事録／要望書／仕様書／設計書／調査メモ／データ／コード／テスト結果／報告書／その他）、用途 `multi`（入力／作業途中／検証・記録／最終成果）、状態 `select`（下書き／レビュー中／承認済み／廃止）、所在 `text`、保存先 `text`、共有URL `url`、版 `text`、ハッシュ `text`、要約（1行） `text`、作成者 `rel(👥)`、最終編集者 `rel(👥)`、関連タスク `rel(✅)`、関連する決定 `rel(🗂)`、根拠にしているナレッジ `rel(🧠)`
- 種類の選択肢は版 2 のまま（「議事録」を残す。版 2 から移した行が持つため）。新しく議事録を登録するときは使わず、📝 議事録に置く。

**📝 議事録**: 会議名 `title`、ID `uid`、開催日時 `date`（開始・終了）、会議の種類 `select`（定例／キックオフ／レビュー／顧客打合せ／社内検討／その他）、状態 `select`（原文のみ／確定／取消）、参加者 `rel(👥)`、社外参加者 `text`、要約（1行） `text`、決定事項 `rel(🗂、双方向。🗂 側は 出典議事録)`、タスク `rel(✅、双方向。✅ 側は 出典議事録)`、関連ナレッジ `rel(🧠)`、関連アーティファクト `rel(📄)`、原文の所在 `text`、原文のハッシュ `text`、元の記録 `url`、使った設定 `text`、他のプロジェクト `rel(📁)`、記録者 `rel(👥)`、代理AI経由 `check`
- 新規作成でも、双方向リレーションの組は移行の A-1・A-2 と同じ順で作る: 🗂・✅ を作った後に 📝 を双方向リレーション（決定事項・タスク）以外で作り、双方向リレーションを 📝 側から 1 本ずつ張って 🗂・✅ 側の名前を「出典議事録」にする（両側を別々に作ると片方向のリレーションが 2 本できる）。

**⚙️ ワークフロー設定**: 名前 `title`、ID `uid`、種類 `select`（辞書／書式テンプレート／抽出・判断ルール／参照情報）、対象ワークフロー `multi`（全ワークフロー／C0〜C6／E1〜E5／M1〜M7）、状態 `select`（有効／下書き／無効）、版 `num`、管理者 `rel(👥)`、更新日時 `edited`

**📰 デイリーサマリー**: 日付 `title`、ID `uid`、状態 `select`（順調／注意／要判断）、期限切れ件数 `num`、未対応の判断依頼件数 `num`（種別 `request` で状態が `todo`／`in_progress` のタスクの件数）

**🧾 実行ログ**: 実行 `title`（run_id）、ワークフロー `select`（C0〜C6／E1〜E5／M1〜M7）、実行者 `rel(👥)`、開始 `date`、終了 `date`、結果 `select`（成功／一部失敗／失敗）、定期実行 `check`、適用 `num`、保留 `num`、失敗 `num`、版の変更 `text`

### トップページの雛形

トップページを作るときは、本文の先頭に次の 2 つをこの順で書く。

| 見出し | 作成時の中身 | 以後 |
| --- | --- | --- |
| 📌 プロジェクト概要 | 目的: （マネージャーが記入） / 主な制約: （マネージャーが記入） / クライアント: <クライアント名> / プロジェクトキー: <プロジェクトキー> | マネージャーが手で書く。ACT は書き換えない |

## 手作業が必要な設定（`manual_steps`）

API では設定できないもの、人が書くものを、`plan` の `manual_steps` として案内する。

1. 👥 メンバー: マネージャー・ビジネスオーナーを「編集可」、他のメンバーを「コメント可」にする（役割はマネージャーが設定する。参加者は自分を `worker` で登録する）。
2. 🧠 ナレッジ: DB 全体をメンバーに「コメント可」にし、行単位の権限ルールで「所有者（Person）に一致 → 編集可」を設定する（プランによっては使えない）。
3. 🗂 決定事項: マネージャー・ビジネスオーナーを「編集可」、他のメンバーを「コメント可」にする。
4. ⚙️ ワークフロー設定: DB をマネージャー「編集可」、他メンバー「コメント可」にし、辞書のページだけ全員「編集可」にする。
5. 🏷 タグ: 全メンバーを「編集可」にする（削除禁止はプラグイン側の規則と M7 の見直しで守る）。
6. 🧾 実行ログ: 全メンバーを「編集可」にする（各自の実行が行を書くため）。
7. 🔧 ACT 設定: マネージャー・ビジネスオーナーだけ「編集可」にする。
8. 各 DB（📝 議事録を含む）の本文テンプレートを Notion の DB テンプレートとして登録する（人が手で作るときも同じ見出しになる）。
9. プロジェクトのトップページ: 📌 プロジェクト概要の「目的」「主な制約」をマネージャーが記入する（雛形では「（マネージャーが記入）」のまま）。
10. 📝 議事録: 全メンバーを「編集可」にする。取消（マネージャー・ビジネスオーナーだけ）と、確定後の清書を書き換えない規則は、プラグイン側で守る。
11. 📝 議事録（版 2 → 3 の移行で開催日時を空にした行があるときだけ）: 開催日時が空の 📝 に開催日時を記入する。対象は C-1 の `targets` のうち `note` が `要記入:` で始まる行と、`写し済み（飛ばす）` の行のうち 📝 の開催日時が空のもの。件数と会議名を添えて案内する。

## 版 2 → 3 の移行手順

`plan` の「更新」で、`recorded_schema_version` が 2 のときに並べる変更。分類は 追加／変換／削除／手作業。版 1 の保存先は、`schema-v2.md` の版 1 → 2 の移行手順の後に続けて、この手順を並べる（1 版ずつ）。

| 変更 ID | 対象 | 分類 | 内容 |
| --- | --- | --- | --- |
| A-1 | プロジェクト | 追加 | 📝 議事録 DB を、上のプロパティのうち双方向リレーション（決定事項・タスク）以外で作る（ID の接頭辞 `<KEY>-MTG` の照合を通す） |
| A-2 | 📝・🗂・✅ | 追加 | 📝 に「決定事項」「タスク」を双方向リレーションとして足し、🗂・✅ 側の名前を「出典議事録」にする（プロパティ名の変更と追加を 1 回の更新に混ぜない） |
| A-3 | 共通 DB | 追加 | 説明文の印の版を `notion/3` にする（構成は変えない） |
| C-1 | 📄 → 📝 | 変換 | 📄 の種類「議事録」の行ごとに 📝 のページを 1 件作る（詳細は下記「C-1 の写し方」）。元の行が指す清書ファイルは動かさない |
| C-2 | 🗂・✅ | 変換 | 出典アーティファクト（🗂）または入力（✅）が C-1 の元の行を指す決定・タスクを、その行から作った 📝 の「決定事項」「タスク」に足す（🗂・✅ 側の出典議事録が付く）。元のリレーションは残す |
| C-3 | 📄 | 変換 | C-1 の元の行の状態を「廃止」にし、本文「所在と版」の末尾に「<移行日> 📝 <会議名> に移した」とメンションを追記する。元の行は削除しない |
| M-1 | 📝 | 手作業 | 上の手作業の設定のうち 📝 に関わるもの（8 の DB テンプレートの登録、10 の権限）を行う |
| M-2 | 📝 | 手作業 | 開催日時が空の 📝 に開催日時を記入する（上の手作業の設定の 11）。11 の対象が 1 件以上あるときだけ並べ、11 を対象の件数と会議名付きで `manual_steps` に入れる |

### C-1 の写し方

- **プロパティ**: 名称 → 会議名、要約（1行） → 要約（1行）、関連タスク → タスク、関連する決定 → 決定事項、根拠にしているナレッジ → 関連ナレッジ、作成者 → 記録者、代理AI経由 → 代理AI経由、元の 📄 の行 → 関連アーティファクト（照合キー）。状態は「確定」。原文の所在・原文のハッシュ・元の記録は空。
- **開催日時**: 所在のファイル名の先頭の `YYYY-MM-DD` から取る。取れなければ空にする（M-2 で人が記入する）。
- **会議の種類**: 会議名に「定例」「キックオフ」「レビュー」を含めばそれ、それ以外は「その他」。
- **本文**: 📌 要点 ← 要約と抽出したコンテキスト、議題 ← 主な内容、決定事項・宿題・持ち帰り・要確認は見出しだけ、原文と訂正履歴 ← 「<移行日> 版 2 → 3 の移行で作成。移行元: <📄 の ID とメンション>。旧形式の清書ファイル: <所在>（中身は本文に展開していない）」。
- **`plan` に載せるもの**: 📄 の種類「議事録」の全行を `targets` に、3 件程度を `samples` に入れる。`targets` の `note` は行ごとに次のどれか 1 つにする。
  - 元の行を関連アーティファクトに持つ 📝 が既にある行: `写し済み（飛ばす）`
  - 開催日時が取れない行: `要記入: 開催日時（ファイル名から取れないため空にする）`（`要記入:` は値を空にする行の印。`act-core:store-protocol` の `targets` の定義に従う）
  - それ以外: `開催日時: <YYYY-MM-DD>`

### 冪等・再開

- **行ごとの照合**: C-1 は、元の行を関連アーティファクトに持つ 📝 があればその行を書かずに飛ばす。C-2 は、足すリレーションが既に付いている決定・タスクを飛ばす。C-3 は、既に「廃止」で追記がある行を飛ばす。どの変換も、写した後に値を元の行と照合する。
- **変更ごとの結果**（`apply` の `results` は変更 ID ごとに 1 件）: 変換（C-1〜C-3）は、対象の全行を飛ばしたなら `already_applied`、1 行でも失敗したら `failed`（失敗した行を結果の詳細に書く）、それ以外は `success`。A-1 は、このプロジェクトのトップページの下に `[ACT] type=minutes` の印の 📝 が既にあれば作らずに `already_applied`。A-2 は双方向リレーションが既にあれば、A-3 は印の版が既に `notion/3` なら `already_applied`。
- **作り直した計画**: 途中で止まった保存先は 🔧 ACT 設定の `schema` が `notion/2` のままなので、次の `plan` で同じ変更が並び、適用済みの分は上のとおり飛ばされる。このとき、A-1 の ID の接頭辞の照合では、このプロジェクトのトップページの下にある `[ACT] type=minutes` の印の 📝 が使う `<KEY>-MTG` を衝突に数えない（前回の適用で作った自分の DB のため）。
