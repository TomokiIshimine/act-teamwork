# 初回の構成案の作り方

構成が `unconfigured` のプロジェクトで、初めて置き場所を作るときだけ読む。規則の要点は `SKILL.md`「初回の構成案」と「置き場所の付け方」が正で、ここではその進め方と例を示す。

## 進め方

1. **材料を集める。** プロジェクトの名前・クライアント（`project.yaml` の `project.name`・`client`）、既存のタスクと 📄 アーティファクトの名前（`act-core:store-protocol` の `query`。読むだけ）、今回置くファイルの内容（題名・見出し・要約）。
2. **テーマを洗い出す。** 材料から、プロジェクトで繰り返し出てくる内容のまとまりを挙げる。今回のファイルだけでなく、タスクと既存の成果物の名前から今後置かれそうなテーマも拾う。
3. **第 1 階層を 3〜7 個に絞る。** 似たテーマはまとめ、1 つの資料しか入らなそうなテーマは近いものに含める。用途（入力・作業途中・成果物）、日付、人名、状態で分けていないかを確かめる。
4. **各置き場所に目的を 1 行で書く。** 「何の資料を置くか」が分かる文にする。目的は次回以降の振り分けの基準になるので、境界の紛らわしい置き場所どうしは置くものの違いが分かるように書く。
5. **今回のファイルの置き場所を決める。** 第 1 階層の目的と照合して選ぶ。第 1 階層の中でさらに分けたほうがよいときだけ、第 2 階層を作る（今回のファイルに要るものだけ）。
6. **構成案の形にまとめる。** `SKILL.md`「出力の形」の構成案に、作るすべての置き場所（根の `folder_root` を含む）を親から順に並べる。既にあるものは `create: false`。

## 確認の取り方

- 構成案は、書き込み計画に確認要の 1 項目として載せ、木の形（置き場所と目的）で示す。
- 利用者の修正は自由記述（例:「顧客要望と評価を分けて」「調査は 1 つにまとめて」）で受け取り、それを材料に加えて構成案を作り直す。
- 構成の設定（`project.yaml` の変更）・各置き場所の作成・ファイルの配置は、構成案の項目に依存する項目として並べる。構成案が採用されなければ、ファイルは従来の固定パスで計画する。
- 構成案は採用され、一部の置き場所の作成だけが採用されなかったときは、そこに置く予定だったファイルの置き場所を、採用された置き場所から `SKILL.md`「置き場所の選択」の規則で選び直して計画する。どの段で計画し直すかは呼び出し元が決める。

## 例

材料: プロジェクト「社内FAQ AI検証」（クライアント みなと商事）。既存タスク「FAQ データの収集」「回答精度の評価」「PoC 報告書の作成」。今回のファイル「要望書_問い合わせ対応AI.pdf」。

```text
library/                  ACT が整理するプロジェクトの資料の根
├── 要望と要件/            顧客からの要望書・要件定義・仕様の合意事項
├── FAQデータ/             FAQ の元データ・整形済みデータ・データの説明
├── 評価/                  評価の計画・評価用の質問集・評価結果
├── 調査/                  技術・製品・事例の調査メモ
└── 報告/                  中間報告・PoC 報告書・説明資料
```

- 今回のファイルは `要望と要件/` に置く。第 2 階層は要らない。
- `folder_root` と `layout` は `SKILL.md`「初回の構成案」のとおり（`folder_root: library`）。
- 予定パス: `library/要望と要件/要望書_問い合わせ対応AI.pdf`（`{folder}` = `要望と要件`）。

### 避ける例

| 案 | 避ける理由 |
| --- | --- |
| `入力/`・`作業中/`・`成果物/` | 用途で分けている。同じテーマの資料が 3 か所に分かれる |
| `2026-10/`・`2026-11/` | 日付で分けている。日付はファイル名とメタ情報で表す |
| `鈴木さん/` | 人名で分けている。担当はメタ情報で表す |
| `承認済み/`・`下書き/` | 状態で分けている。状態が変わるたびに移動が要る |
| `要望書_問い合わせ対応AI/` | 1 つの資料のための置き場所。テーマ（一般名詞）にする |
| 第 1 階層が 12 個 | 多すぎて振り分けに迷う。まとめて 7 個以内にする |
